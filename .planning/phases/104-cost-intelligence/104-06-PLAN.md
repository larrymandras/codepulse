`projectPeriodEndSpend(spend, elapsedHours, periodHours, limitValue, periodStartSec)` — the exact
`projectDayEndSpend` algorithm with `24` replaced by `periodHours` and the module constant
`DAILY_CAP` replaced by `limitValue`:
- `elapsedHours <= 0` → `{ projectedTotal: 0, willExceed: false, projectedHitTime: null }`.
- `hourlyRate = spend / elapsedHours`; `projectedTotal = hourlyRate * periodHours`;
  `willExceed = projectedTotal > limitValue`.
- `projectedHitTime = willExceed && hourlyRate > 0
     ? new Date((periodStartSec + (limitValue / hourlyRate) * 3600) * 1000) : null`.
  Note this uses the caller's `periodStartSec`, not a re-derived day start — a weekly or monthly
  budget must project onto its own period origin.

- `projectedTotal >= limitValue` → `"warning"` (D-13 spike: the burn rate projects past the limit
  before the period ends, even though actual spend has not yet reached the warn fraction).

severity. Put a comment on the third branch naming D-13, because it is the only branch that is not

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| cron scheduler → `computeHourly` → `evaluateBudgets` | No external caller. The untrusted inputs are the operator-authored budget rows and the ingested telemetry volume behind the spend figure. |
| `evaluateBudgets` → `alerts` table → `sendAlertWebhook` | An insert here causes an outbound webhook to a configured channel; a fire loop would become an outbound message flood. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-104-23 | Denial of Service | `evaluateBudgets` inside `computeHourly` | mitigate | The concrete new reads are: one whole-table `costBudgets.collect()` (low double-digit rows by design), one `computePeriodSpend` per USD budget bounded to ~31 daily plus ~24 hourly bucket-sets (plan 104-05 T-104-19), one `.take(1)` per quota budget, and one `alerts.by_source` index read per firing candidate. That is a small bounded addition, NOT "no new reads" — the honest claim RESEARCH.md Pitfall 5 asks for. Live execution timing against the self-hosted instance is verified in plan 104-11 and is not inferred from the unit suite. |

| T-104-25 | Denial of Service | a throwing `evaluateBudgets` failing the whole hourly cron | mitigate | Two layers: a per-budget-row try/catch inside `evaluateBudgets`, and an outer try/catch at the `computeHourly` call site.
