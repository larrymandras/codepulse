## Scope note — the v15.0 "Borealis Console" overhaul is explicitly NOT used here

`Skill("sketch-findings-codepulse")` documents a validated but **unbuilt** v15.0 direction
("Borealis Console": `--surface-0/1/2/3` layering, aurora Signal Horizon, Pulse ECG hero, italic-serif
Ástríðr voice, ~80% primary-usage cut). Repo `CLAUDE.md`'s own Design Findings section says build
sequencing holds the entire overhaul — including its quick-wins — for v15.0, and 116-CONTEXT.md's
`<domain>` out-of-scope list repeats this a third time. Phase 116 is a v14.0 phase.

This document therefore specifies Galdr entirely against the **current, shipped** design system —
Tailwind 4 + shadcn/ui (New York), the live CSS vars in `src/index.css`, and the live component
inventory in `src/components/ui/`. No Borealis token (`--surface-*`, the aurora/ECG signatures, the
serif voice, the 80% cut) appears anywhere below. Where a choice below happens to also be
forward-compatible with the future overhaul, that is incidental, not a design goal of this phase.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 | 1.5 |
| Mono label (chips, eyebrows, nav-style buttons) | 12px (`text-xs`), mono, uppercase, `tracking-widest` | 700 | 1.4 |
| Page heading | 24px (`text-2xl`) | 700 | 1.3 |

**Two weights, declared and authored by this phase: 400 (Body) and 700 (Mono label / Page
heading).** 400/700 is the mono-chip idiom this phase clones verbatim from `SkillFilterChips.tsx:50`
(`font-mono font-bold`) and `SkillRow.tsx:139` (`font-mono font-bold text-sm`). No 3rd or 4th weight
is introduced anywhere in Galdr's own type scale.

**Inherited primitive chrome — deliberately excluded from the table above, recorded here so it is
not "fixed" into an override later.** The editor drawer's `SheetTitle` and the fill-in/archive
dialogs' `DialogTitle` render at shadcn's untouched default — `text-lg leading-none font-semibold`
(18px / weight 600 / line height 1.2), `src/components/ui/dialog.tsx:126`. Galdr applies **no**
typographic override to either primitive; this is inherited component chrome, not a Galdr-authored
type role, so it does not belong in — and is not counted toward — the authored type scale above. If a
future editor or planner notices this weight "doesn't match the table," the correct read is that the
table doesn't govern it, not that it needs styling to conform.

Prompt body / slug / variable-name text uses **JetBrains Mono** (repo's designated code font,
`CLAUDE.md` "Styling"); prose (descriptions, empty-state copy, dialog body text) uses Geist at the
Body role above.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--background)` / `var(--card)` | Page background, card surfaces, drawer background |
| Secondary (30%) | `var(--muted)` / `var(--border)` | Card borders, chip idle borders, drawer section dividers, empty-state panel background (`bg-primary/5` per `AllSkillsOverview.tsx:58` idiom, still primary-derived at low opacity — see accent note) |
| Accent (10%) | `var(--primary)` | See reserved-for list below |
| Destructive | `var(--destructive)` | Archive button + confirm dialog action only (see note) |

**Accent (`var(--primary)`) reserved for — explicit list, nothing else:**
- Search input focus border/ring (`SkillRow`-adjacent idiom, `Skills.tsx:583`)
- Active category/filter chip fill (`bg-primary/15` or `/20`) + border + `var(--glow-xs)` (`SkillFilterChips.tsx:52`)
- Selected/focused card border on the grid
- "New Prompt" primary CTA button
- The enabled state of the Copy button and the "Send to Chat" button inside the variable
  fill-in dialog (disabled state uses `var(--muted-foreground)`, never accent)
- Favorite star fill, when favorited — **deviation from the Skills donor, stated explicitly below**

**Primary visual anchor (Dimension 2 focal point), declared explicitly.** The `/galdr` grid's focal
point is the **"New Prompt" CTA** (top-right of `PageHeader`, accent-filled per the list above),
paired with the **selected/focused card's accent border** once a card is active. These are the only
two accent-saturated elements on an otherwise 60/30-dominant page — the eye has exactly one place to
land in each of the page's two states (browsing the grid vs. one card actively selected/focused). No
other element on this page competes for that saturation.

**Favorite star color — deliberate deviation from the Skills donor.** `SkillRow.tsx:143`/`:174`
hardcodes `fill-amber-400 text-amber-400` for favorited stars — a literal Tailwind color, not a CSS
var, which contradicts `CLAUDE.md`'s own standing rule ("never hardcode hex... use `--status-*`").
Galdr's favorite star uses **`var(--status-warn)`** instead (fill + stroke), which resolves to a
near-identical amber/gold across every dark theme (`#eab308` cyan, `#f59e0b` amber, `#fbbf24`
readable/aubergine — `src/index.css:97,168,219,258,321`) with no perceptible UX difference, and
brings the favorite star into token compliance rather than perpetuating an existing lint-level
inconsistency. This is the one point where Galdr does not pixel-clone Skills; every other visual
borrowed from Skills is unchanged.

**Destructive note:** the Archive action is styled `variant="destructive"` (`var(--destructive)`),
matching the existing bulk-archive precedent (`Skills.tsx:707-713`, `variant="destructive"` on an
"Archive N" button) even though D-16's archive is non-permanent (data retained, just hidden). This
matches how this repo already treats "archive" visually — destructive-styled because it removes the
item from normal view, not because it is unrecoverable. It does **not** get the type-to-confirm
treatment (`DeleteSkillDialog.tsx`) — that pattern is reserved for the genuinely-irreversible hard
delete this phase does not build (D-16).

**Semantic channel (no new token introduced):**

| Token | Usage |
|-------|-------|
| `var(--status-ok)` | Not used this phase (no live/health signal on this surface) |
| `var(--status-warn)` | Favorite star fill (see above); the "unresolved variable" chip state in the fill-in dialog |
| `var(--status-error)` | Copy/Send failure toast icon (clipboard write failure — mirrors `SkillRow.tsx`'s `copyState === "failed"` treatment) |
| `var(--status-info)` | Not used this phase |

| Element | Copy |
|---------|------|
| Primary CTA | **"New Prompt"** (opens the editor drawer in create mode) |
| Search placeholder | "Search prompts..." (matches `Skills.tsx:580` "Filter skills..." convention, verb adjusted for Galdr's search-not-filter framing since search also full-text-matches body, not just name) |
| Empty state heading (true empty — zero prompts exist) | **"No prompts yet"** |
| Empty state body | "Save one from Claude Code with `/galdr-save <title>`, or create one here." + "New Prompt" button (mirrors `Skills.tsx:489-501`'s `needsSeed` panel shape) |
| Empty state — search/filter matches nothing (prompts exist, none match) | **"[ NO PROMPTS MATCH ]"** — mono, dashed border, `border-primary/20 bg-primary/5` treatment (verbatim reuse of `AllSkillsOverview.tsx:56-60`'s existing "no results" idiom) |
| Loading state | Skeleton cards (`src/components/ui/skeleton.tsx`, shaped like the real card: title bar + 2 body lines + chip row) — never a bare spinner, never blank |

| Copy button — every variable filled | "Copy" → flips to "Copied" for 1.8s on success, "Failed" on clipboard error (reuses `SkillRow.tsx`'s exact `CopyState` idle/copied/failed timing and labels) |
| Copy button — unresolved variable(s) present (D-11) | Button `disabled`; helper text below the form: "Fill in every variable to enable Copy." |
| "Copy as command" | Always enabled (no variable resolution — it copies the literal `/galdr <slug>` string, not the body). Label: "Copy as command" → "Copied" for 1.8s on success. |
| Send to Chat — unresolved variable(s) present (D-11/D-12) | Button `disabled`, same helper text as Copy: "Fill in every variable to enable Send." |
| Send to Chat — success | Navigates to `/chat` with a resolved-body `autoSend` handoff (reuses the existing `RunTargetChooser`/`Chat.tsx:541-584` mechanism: `navigate("/chat", { state: { autoSend: { text, ... } } })`) — no separate Galdr-side toast; Chat's existing auto-send flow owns confirmation |
| Destructive confirmation — Archive | Title: `Archive "{title}"?` · Body: "Hidden from the grid and from skill lookup. The prompt and its version history are retained — nothing is deleted." · Action button: "Archive" (`variant="destructive"`, no type-to-confirm — see Color note above) |
| Slug collision refusal (D-06, surfaces if the UI ever lets a save collide) | "A prompt named \"{existingTitle}\" already exists (updated {relativeDate}). Choose a different title, or edit the existing prompt instead." — never a silent overwrite, never an auto-suffixed slug |
| Version history — restore action | Button: "Restore" → on success, toast: "Restored the {date} version as the new current version." (non-destructive: D-15 makes restore append-only, so no confirm dialog is needed — nothing is lost) |
| Version history — empty (new prompt, no edits yet) | "No earlier versions yet." |

## Component Inventory & Layout

### `/galdr` page (`src/pages/Galdr.tsx`)

```
PageHeader  title="Galdr"  actions=[Search input] [New Prompt button]
Filter chip row  (SkillFilterChips-pattern, single-select, counts)
  chips: All | Favorites | Recently used | {category chips, derived live — see Discretion below}
Card grid  (CSS grid, responsive columns — 1 col mobile, 2 col md, 3 col xl; gap = sm/8px between
            cards, matching Card's own internal py-6 rhythow — no new grid token)
  → one <Card> per prompt (see anatomy below)
Empty / loading / error states per Copywriting Contract, replacing the grid region only —
  PageHeader and chip row remain visible even in the error state, matching `SectionErrorBoundary`'s
  "one failing widget doesn't take down the page" convention (`CLAUDE.md` Patterns)
```

**Card anatomy** (shadcn `Card`/`CardHeader`/`CardTitle`/`CardContent`/`CardFooter`):

```
CardHeader:  [title, Mono-label-adjacent but Body-weight — see note] [Star toggle, top-right]
CardContent: description/body preview (2-line clamp, Body role, --muted-foreground)
             [category chip] [usage count, "N×" tabular-nums — mirrors SkillRow.tsx:161-165]
CardFooter:  [Send split-button, primary] · [⋯ overflow menu: Edit / Archive]
```

Clicking anywhere on the card body (not the footer controls) opens the editor drawer in view/edit
mode — mirrors Skills' row-click-to-edit affordance conceptually, adapted to a card since Galdr uses
a card grid, not `SkillRow`'s list rows (see note below).

**Icon-only control labels (Dimension 2 — accessibility), declared explicitly.** The donor this
phase clones already establishes this convention (`SkillRow.tsx:170` `aria-label={`Toggle favorite
${skill.name}`}`, `:178`, `:190`) — Galdr carries it forward for every icon-only control it adds:

| Control | `aria-label` |
|---|---|
| Card's favorite Star toggle | `Toggle favorite {title}` (verbatim pattern match to `SkillRow.tsx:170`) |
| Card's `⋯` overflow trigger | `More actions for {title}` |
| Send split-button's chevron (opens the 3-target dropdown) | `Choose send target for {title}` |

No icon-only control in this phase ships without a declared label — a bare Lucide icon with no
`aria-label`/`title`/visible text is not an acceptable implementation of any control listed above.

**Card grid vs. Skills' list rows — resolving an apparent conflict with "clone the Skills UX."**
Design doc §4.1 explicitly says Galdr's UI is a "searchable/filterable **card grid**," while the
literal Skills DOM (`SkillRow.tsx`) is list-row-based, not card-based. This document reads "clone the
Skills UX" as **borrowing Skills' interaction patterns** (single search input filtering the whole
set, single-select smart-view chips, favorite toggle, drawer-based editing, hover-reveal secondary
actions) — not its literal row markup. Galdr therefore composes shadcn `Card` in a CSS grid, per the
design doc's explicit instruction, while the interactions above are verbatim-borrowed from Skills.

### Editor drawer (Sheet, `src/components/galdr/PromptEditorDrawer.tsx`)

```
<Sheet side="right">
  <SheetContent className="w-full sm:max-w-2xl overflow-y-auto">
    SheetHeader: SheetTitle = "New Prompt" | "Edit Prompt" · SheetDescription (optional, category context)
    Title input · Category input (freeform, see Discretion) · Tags (optional, if scoped in)
    Body editor: <Textarea> (mono font, generous min-height, e.g. 12 rows)
    Detected-variables chip row: read-only reflection of every {{name}} found in the body,
       auto-updates on every keystroke (debounced), e.g. [company] [industry] — chips use the
       Mono-label typography role, --muted-foreground border, NOT the primary accent (these are
       informational, not interactive — editing a variable means editing the {{name}} in the body)
    Preview panel (Collapsible, default OPEN — unlike version history, since preview is the
       primary editing feedback loop): live-renders the body with each detected variable's current
       fill-in value substituted; unfilled variables render as their {{name}} highlighted in
       --status-warn to make "still a placeholder" visually obvious while editing
    Version history (Collapsible, default COLLAPSED — same reveal-on-demand convention as
       109-UI-SPEC §H's Settings swap-history section, reusing the same `collapsible.tsx` primitive):
       trigger row "Version history (N)" — real count, never rounded; rows: [date] [Restore button]
    SheetFooter: [Archive button, destructive, left] ... [Save button, primary, right]
```

Width override precedent: `w-full sm:max-w-2xl` follows the established repo pattern of overriding
`SheetContent`'s narrow `sm:max-w-sm` default per-consumer (`AlertRuleForm.tsx:282` uses
`w-[480px]`, `IntakeSheet.tsx:40` uses `w-full sm:max-w-xl`) — Galdr's drawer is wider than
`IntakeSheet`'s because it stacks a body editor + preview + version history, none of which `IntakeSheet`
carries.

### Variable fill-in dialog (shared by Copy and Send-to-Chat — `src/components/galdr/FillVariablesDialog.tsx`)

One shared component gates both D-11 (Copy) and D-12 (Send-to-Chat), since both rules are "one
contract, not two" per 116-CONTEXT.md's own framing of D-09–D-12. Built on shadcn `Dialog` (not
`Popover` — unlike `RunChatPopover.tsx`'s single-field precedent, this form can have N fields, one
per detected variable, so it needs a full modal, not an anchored popover):

```
<Dialog>
  DialogHeader: DialogTitle = "Fill in variables — {promptTitle}"
  One <Input> per detected {{variable}}, labeled by variable name, mono placeholder showing the
    variable name itself (e.g. placeholder="company")
  Live preview of the resolved body below the fields (same substitution logic as the drawer's
    preview panel — extract as a shared pure function, not duplicated)
  DialogFooter: [Cancel] ... [Copy | Send to Chat] — disabled until every field is non-empty
    (trim-checked, matching D-10/D-11's "unresolved variable" definition: an empty or
    whitespace-only value does not count as resolved)
</Dialog>
```

**Send-to-Chat is a blocking step, not a fire-and-forget popover — this is load-bearing, not a
style choice.** 116-CONTEXT.md D-12 states the existing `Chat.tsx:541-584` auto-send handoff fires
immediately on arrival (`firedRef` guard, no user confirmation step in Chat itself) — so an
unresolved body handed to that handoff would be answered by Ástríðr before anyone could correct it.
This dialog is therefore the **only** place variable resolution can happen for the Chat target; there
is no "send now, fix later" path. The dialog does not close and no navigation occurs until the button
is clicked with every field filled.

### "Send" split-button (three targets — `src/components/galdr/SendSplitButton.tsx`)

Pattern-matches `RunTargetChooser.tsx`'s dropdown-trigger shape (same `DropdownMenu` primitive,
same 3-row `DropdownMenuItem` list with a leading icon), but with Galdr's own three targets, not
Skills' Chat/Forge/Ástríðr set:

```
[Send ▾]  (primary button, split — main click = last-used target, chevron opens the dropdown)
  DropdownMenuItem  MessageSquare icon  "Send to Chat"       → opens FillVariablesDialog (chat mode)
  DropdownMenuItem  Copy icon           "Copy"                → opens FillVariablesDialog (copy mode)
  DropdownMenuItem  Terminal icon       "Copy as command"     → immediate clipboard write, no dialog
```

The chevron segment carries its own `aria-label` (`Choose send target for {title}`, see the
Icon-only control labels table above) distinct from the main button's own accessible name (which
reads as "Send" plus whatever the last-used target's label is).

`Terminal` and `MessageSquare` are already imported project-wide (`navRegistry.ts:31,43`); `Copy` is
a standard `lucide-react` export not yet imported anywhere in this file set — first use here, no new
dependency.

### Archive confirmation (`AlertDialog`, not a new dialog type)

Built on shadcn `alert-dialog.tsx` (already installed, already used by `DeleteSkillDialog.tsx` and
the bulk-archive dialog at `Skills.tsx:680-716`) — **not** `DeleteSkillDialog`'s type-to-confirm
pattern (that primitive is reserved for genuinely irreversible hard delete, which D-16 does not
build). A single "Archive" / "Cancel" button pair, copy per the Copywriting Contract table above.

## States

| Surface | Empty | Loading | Error |
|---|---|---|---|
| `/galdr` grid | "No prompts yet" panel (zero prompts) or "[ NO PROMPTS MATCH ]" (filtered to zero) | Skeleton cards (3–6, matching card anatomy) | "Couldn't load prompts..." banner, PageHeader/chips stay interactive |
| Editor drawer, version history | "No earlier versions yet." | Skeleton rows inside the Collapsible while its own query resolves | Inline text, no modal: "Couldn't load version history." |
| Fill-in dialog | N/A (always has ≥1 field once opened — a prompt with zero variables never triggers this dialog; Copy/Send fire immediately for such prompts, see note below) | N/A (fields render synchronously from the already-loaded prompt) | Clipboard write failure → "Failed" button state + `var(--status-error)`, 1.8s, matching `SkillRow.tsx`'s existing failed-copy treatment; navigation failure is not a realistic case (client-side `navigate()` cannot fail) |

**Zero-variable prompts skip the fill-in dialog entirely.** D-10/D-11/D-12 exist to block a
*half-filled* body from reaching Copy/Chat — a prompt with no `{{variables}}` at all has nothing to
fill in, so Copy and Send to Chat both act immediately for such prompts (Copy → clipboard, Send →
navigate with the literal body). This is not a new decision; it is the D-11 disabled-rule's own
vacuous-truth case ("every variable has a value" is trivially true when there are zero variables),
stated explicitly so the planner does not build a dialog that always shows zero fields.

## Claude's Discretion — resolved

Per 116-CONTEXT.md's discretion list, decided here with reasoning (planner should treat these as
settled, not re-litigate):

**Category model → plain `category: v.string()` field, not the `skillCategories`-style table.**
The heavier pattern exists in Skills because skills are numerous (100+), auto-classified by an
intake pipeline, and need per-category color/icon/sortOrder administration plus drag-drop
reassignment (`Skills.tsx:78-79`, `CategoryGrid.tsx`). None of that applies to a curated,
agent-authored prompt library — D-08 explicitly caps the skill surface with no `--category` flag,
and prompts are saved one at a time via `/galdr-save`. A plain string field is simpler and
sufficient. **UI consequence:** category chips in the filter row are derived at render time from the
live distinct `category` values already present in `prompts` (same "smart view" derivation
`SkillFilterChips` already does for `mostused`/`unused`/`recent`), not from a separately administered
categories table — there is no category color/icon admin UI in this phase.

**`usageCount` semantics → increments only on actual body delivery, never on listing/viewing.**
Bumped exactly when: (a) the skill injects a resolved body (`/galdr <slug>`, already specified by
D-08), (b) the UI's Copy action fires with every variable resolved, (c) the UI's Send-to-Chat action
fires with every variable resolved. **Not** bumped by: opening the card, opening the editor drawer,
toggling favorite, or "Copy as command" (which copies the invocation string, not the resolved body —
the eventual `/galdr <slug>` run is what will bump it). This makes the number mean one specific
thing — "this prompt's body was actually delivered somewhere N times" — consistently across every
surface, as 116-CONTEXT.md's discretion note requires. `lastUsedAt` updates on the same trigger.
Schema comment (for the planner to carry into `convex/schema.ts`): `usageCount: v.number(), //
incremented only on resolved-body delivery: skill injection, UI Copy, UI Send-to-Chat — never on
listing, viewing, favoriting, or "Copy as command".`

**Nav placement / icon → COMMAND group, after Skills, `Sparkles` icon.** See Nav Registry section
above. `Sparkles` reads as "magic/AI-generated content" already inside this codebase's icon
vocabulary (used for the Ástríðr dispatch target, `RunTargetChooser.tsx:20`) and is unclaimed in
`iconComponents` — a fitting, low-risk match for Galdr's "chanted spells" naming without inventing a
new icon idiom.

**Seeding → begin empty, no starter prompts.** Fabricated/placeholder content is a standing
anti-pattern in this repo (the (inapplicable-here) sketch findings' own kill list names "fabricated
data" explicitly, and no other v14.0 phase ships seed rows for a user-content table). The empty-state
copy above ("Save one from Claude Code... or create one here") gives a real path to non-empty, so an
empty first-run state is not a dead end.

**Naming hygiene → confirmed no collision risk in this document.** This UI-SPEC refers to the new
tables only as `prompts`/`promptVersions` and never abbreviates to a bare "prompts" that could be
confused with the unrelated `promptSubmissions` table (`convex/schema.ts:651`, hook telemetry) — the
planner should carry the same discipline into component/hook/file names (e.g. `useGaldrPrompts`, not
`usePrompts`).

## Open items for the planner (flagged, not resolved)

- **No "Archived" view exists in this phase's UI scope.** D-16 hides archived prompts from the grid
  and from skill lookup, and the standing "archive, don't rm" rule this decision cites (applied to
  skills and the vault) DOES pair with a restore view there (Skills' Cold Storage). This document
  does not add an equivalent for Galdr, because neither 116-CONTEXT.md's `<domain>` in-scope list nor
  design doc §4.1's UI bullet mentions one — adding it would be scope creep beyond what was asked.
  Net effect: once archived, a prompt is retained in the database (nothing is deleted, versions
  survive) but is **not reachable again from the CodePulse UI this phase** — only a direct Convex
  console/dashboard action could un-archive it. The Archive confirm-dialog copy above is written to
  be honest about this (it promises retention, not UI-visible recoverability). If this gap matters in
  practice, the minimal fix is one more filter chip ("Archived") plus an "Unarchive" row action —
  small, and consistent with the chip-row pattern already specified above — but it is not decided
  here and should not be silently added during planning without confirming it's wanted.
- **Tags field.** Design doc §4.1's schema list includes `tags[]` on `prompts`, but neither the
  design doc's UI paragraph nor 116-CONTEXT.md's in-scope UI bullet mentions a tags UI (only category
  chips, favorites, usage sort). This document specifies the editor drawer's Title/Category/Body
  fields plus an *optional* Tags input, left to the planner to include or defer — if deferred, the
  schema field can still exist unused without breaking anything else in this contract.
