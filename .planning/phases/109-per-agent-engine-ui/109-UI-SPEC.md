## Surface-by-Surface Contract

### §A. The honest absent/unknown state (D-07, ENGINE-03 success criterion 3)

**Defect found during research, not hypothetical.** Today three different strings render for the
identical "no telemetry yet for this profile" condition, and they disagree with each other:

- `BrainHeaderBadge.tsx:114` — `"No brain reported"`
- `Chat.tsx:184-186` (`BrainComposerPill`'s `baseLabel`) — `"Auto"`
- `Settings.tsx:282-287` — `"Not reported"` (already correct, already shipped)
- `BrainPicker.tsx:426` (trigger `baseLabel`) — `"Auto"`

`"Auto"` is the more serious defect of the three: it reads as "the system picked one for you,"
which is a fabricated claim about a resolution that never happened — exactly the class of
dishonesty ENGINE-03 SC3 exists to remove. It is also literally load-bearing in one place —
**corrected 2026-08-07, after the checker flagged that an earlier draft of this document named the
wrong line for this mechanism (confirmed fully resolved on re-check, revision 2; untouched in
revision 3):** `BrainPicker.tsx:358-360`'s
`currentModelDisplayName: engine ? resolveModelDisplayName(currentModel, entries) : "Auto"` ternary
renders the capitalized literal `"Auto"` directly (the `else` branch — `resolveModelDisplayName` is
never called in this case) whenever a profile carries no telemetry, and that field —
`currentModelDisplayName`, not `currentModel` — is what `GlobalSwapModal`'s "current → new" row
actually displays (`GlobalSwapModal.tsx:624`). See §G for the full correction, including a
separate, clearly-labeled note on `currentModel`'s own distinct lowercase `"auto"` fallback
(`:350`), which feeds two other consumers and is a different defect from this one.

**Rule:** every surface that can show "no engine telemetry yet for this profile" renders the exact
same string, **"Not reported"**, italic, `--muted-foreground`, no color dot, no chip. This applies
to (checked against every render site found in code):

- `BrainHeaderBadge.tsx:114` (dashboard-wide badge, `resolved.source === "none"`)
- `Chat.tsx:185` (composer pill, `resolved.source === "none"`) — retires `"Auto"`
- `BrainPicker.tsx:426` (picker trigger's own default `baseLabel`, when not using a custom trigger) — retires `"Auto"`
- `Settings.tsx:282-287` (per-profile row) — no change, this is the correct existing string
- `BrainPicker.tsx:358-360`'s ternary false branch, feeding `GlobalSwapModal`'s confirm-row
  `currentModelDisplayName` column (§G) — retires the rendered `"Auto"` literal

**Accessible name / tooltip:** `aria-label`/tooltip text reads `Active brain: Not reported` with no
parenthetical qualifier. Where a surface already carries a `Tooltip` (badge, `BrainPickerRow`), add
a second line: *"No engine telemetry yet for this profile."* Where a surface has no tooltip today
(Settings row), this document does not require adding one — the italic treatment already
communicates "not a normal reading," and adding a hover affordance to a Settings list row is a
reasonable but non-mandatory enhancement left to the planner's judgment.

**No dot, ever.** All four current implementations already skip the color dot when `model` is
null (`resolved.model ? <dot/> : null` pattern) — this stays exactly as-is; §A only changes the
text, not the dot logic.

### §B. The `source: "override"` rung (D-06) — naming and rendering

**Proposed discriminant name: `"override"`.** `ResolvedBrain.source` (`useResolvedBrain.ts:40`)
currently has 5 members: `"global" | "profile" | "mixed" | "lastTurn" | "none"`. D-06 inserts a new
top rung above `"global"` for the live per-profile override reported over the extended `swap.state`
(D-05). This document proposes the literal value `"override"` — short, and distinct from `"profile"`
(the per-profile *telemetry* rung, unchanged, still fed by `activeEngineSnapshots`) so a future
reader of the code can tell "this profile has a live in-memory pin, read from the override slot"
apart from "this is what the last resolved turn reported." Naming this is otherwise
implementation-only (no visual consequence either way) — the planner may pick a different literal
if there's a reason, as long as every render site treats it per the rule below.

**Rendering rule: `source: "override"` is INVISIBLE to the user — it renders through the exact
same JSX branch as `source: "profile"` with `mode: "pinned"`.** Concretely, in every one of the
three consumers:

- `BrainHeaderBadge.tsx:107` (`isProfile = resolved.source === "profile"`) → extend to
  `resolved.source === "profile" || resolved.source === "override"`. Whatever `mode` value the
  override-rung's `ActiveEngine`-shaped object carries, the render must take the
  `resolved.mode === "pinned"` branch (`BrainHeaderBadge.tsx:197-205`, Pin icon + "pinned default").
  Same for `isConfirmedLive` (`:126-127`) — an override reading is genuinely live server state
  (D-06's "not a D-14 violation" reasoning), so it earns the confirmed-live pulse exactly like a
  telemetry "profile" reading does, once `BRAINS_STUB_ACTIVE` is retired (§E).
- `Chat.tsx` `BrainComposerPill` (`resolved.source === "profile"` checks at `:227`/`:236`) — same
  extension.
- Any Settings-row equivalent that comes to read `useResolvedBrain(profileId)` instead of raw
  `useActiveEngine()` (see §G's precedence note) — same rule.

**Rationale, stated explicitly (per this phase's honesty mandate):** an operator does not need to
know *which resolver rung* answered the question "is this profile pinned to something." Showing
"override" and "profile+pinned" identically is not hiding information — it is correctly reporting
one fact (this profile is pinned to X, right now) that happens to be knowable from two different
live signals. Showing them differently would imply a distinction the operator has no use for and
would violate 103-UI-SPEC §8's "never show both as if both were current" rule in spirit — there are
not two currents here, there is one.

**Picker's `isCurrent` highlight and trigger base label** (`BrainPicker.tsx:558-562`, `:426`) must
also read through the full resolved chain (`useResolvedBrain(profileId).model`), not the raw
`useActiveEngine()` map alone — this is the literal mechanism behind ENGINE-03 success criterion 1's
"the picker's 'This profile' scope... shows a profile's actual current engine." No new visual
element; this is a data-source correction the planner implements per D-06, and this document only
confirms it produces no new UI state beyond what §A/§B already define.

### §C. Per-profile swap outcome state machine (D-05, ENGINE-04) — 5 states, no modal

**Reuse decision, confirmed correct by re-reading `GlobalSwapModal.tsx`:** the global axis's
5-state `GlobalOutcome` union (`pending | confirming | confirmed | accepted | error`,
`GlobalSwapModal.tsx:142-147`) and its `GLOBAL_SWAP_CONFIRM_TIMEOUT_MS = 4000` bound
(`GlobalSwapModal.tsx:157`) are the pattern D-05 requires the per-profile path to reuse. **But the
per-profile path has no modal to render into** — "This profile" scope dispatches directly from the
picker popover (`BrainPicker.tsx:306-327`, `handleProfileDispatch`), which closes immediately
(`handleOpenChange(false)` at `:309`) and shows all further state as a suffix on whichever trigger
is visible (badge / composer pill / Settings row), per 103-UI-SPEC §7's existing shared vocabulary.
This document extends that 3-state vocabulary (pending → confirmed/failed) to the full 5-state one,
compressed to fit a Label-typography suffix:

| Outcome | Suffix | Icon / token | Toast |
|---|---|---|---|
| `pending` | "· switching to {EngineDisplayName}…" | pulsing dot, `--status-info` (unchanged from today) | none |
| `confirming` | **same suffix as `pending`** — deliberately collapsed (see below) | pulsing dot, `--status-info` | none |
| `confirmed` | suffix removed; base label updates to the new engine (via §B's `override`/`profile` reading) | confirmed-live pulse resumes per §B | "{ProfileName} switched to {EngineDisplayName}." (unchanged from today) |
| `accepted` (bounded 4s timeout, **new this phase**) | "· not yet confirmed" | static `AlertTriangle`, `--status-warn` (replaces the pulsing dot — this is the one state that must visually read as "uncertain," never as in-progress or as success) | fires once, at the timeout: "No confirmation yet that {ProfileName} switched to {EngineDisplayName} — it may still be in progress." |
| `error` | suffix removed; base label stays on the real, unchanged, prior engine | none | "Couldn't switch to {EngineDisplayName} — {reason}. {ProfileName} is still on {CurrentEngineDisplayName}." (verbatim 103-UI-SPEC copy, unchanged) |

**Why `pending` and `confirming` collapse to one suffix, documented as a deliberate exception:**
`GlobalSwapModal.tsx:194-206` gives these two states genuinely different copy ("Switching to X…" vs
"Accepted — confirming the switch to X…") because it has a full dialog line to spend. The compact
trigger suffix does not have that room, and the distinction (has the ack arrived yet, vs are we
waiting for the state push) is not information the operator needs to act on — both states are
honestly "not yet true," and 103-UI-SPEC §7's existing rule ("one shared visual vocabulary... never
optimistic") is satisfied by treating them identically. If a future surface has room for the fuller
copy (e.g. if D-10's history section is later extended to show live in-flight rows), it should use
`GlobalSwapModal`'s existing per-state strings rather than inventing new ones.

**Why `accepted` gets its own toast (a genuine addition, not implied by reuse of the BSC-04
pattern):** `GlobalSwapModal` never needs to toast on entering `accepted` because the dialog is
still open and visibly showing the `AlertTriangle` state — the operator is looking at it. The
per-profile path has no modal; the operator may have already closed the popover and moved to another
page. A silent suffix change that only reveals itself on hover fails ENGINE-04's "honest live
status" requirement in practice, not just in principle — the point of this state is that the
operator finds out something is uncertain, not that the system technically recorded the
uncertainty. The toast fires exactly once, at the 4-second boundary, using `sonner`'s
warning-styled toast (matching this codebase's existing `toast.error`/`toast.success` convention —
use whichever `sonner` warning variant is idiomatic here; if none exists yet, a plain `toast()` call
with the copy above is sufficient, no new toast component).

**Persistence:** the `accepted`/"not yet confirmed" suffix has no further timeout. It persists
until either (a) a late confirmation arrives — at which point it resolves to `confirmed` exactly as
if no timeout had occurred, including firing the normal success toast, or (b) the operator starts a
new swap on the same profile, which resets the whole state machine to `pending` for the new target.

### §D. Mixed-state and provider-dot correctness (D-08) — no visual change

`deriveMixedState`'s distinct-model `Set` (`useActiveEngine.ts:49`) and `BrainHeaderBadge`'s
vendor lookup (`BrainHeaderBadge.tsx:96`, `entries?.find((e) => e.id === modelId)`) currently use
raw `===` comparison, so one model reported in two id formats (vendor-prefixed vs bare — the split
documented at `brainsApi.ts:228-231`) reads as two *different* models. This produces a false
**"Mixed brains"** stacked-dot rendering (103-UI-SPEC §2) where a true reading would show a single
agreed engine, and it neutralizes the provider-identity dot to `var(--muted-foreground)`
(`BrainHeaderBadge.tsx:99`'s fallback) for every `inherited`-mode row, because the vendor lookup
also misses.

**This document makes no visual change.** 103-UI-SPEC §2's "Mixed brains" stacked-dot contract and
single-engine dot contract are correct as specified — the defect is purely in which comparison
function feeds them. Once `modelIdsMatch` (D-08) replaces the raw `===` at every listed site
(`BrainHeaderBadge.tsx:96`, `useActiveEngine.ts:49`, `BrainPickerRow`'s `isCurrent`,
`GlobalSwapModal.tsx:502`), the existing rendering rules simply fire correctly. Confirmed no new
color, icon, or copy is needed here.

### §F. Picker grouping — the "Unclassified" group (D-09), and the friction-stacking fix it requires

**Fourth group, appended last, never folded into an existing group.** `GROUP_ORDER`
(`BrainPicker.tsx:182-186`) currently declares 3 fixed groups (Subscription / API / Local, D-07).
Add a 4th:

```
{ group: "unclassified", label: "Unclassified" }
```

Rendered **after** Local, using the exact same `CommandGroup`/heading treatment as the other three
(Heading typography, `.filter((g) => g.entries.length > 0)` — only appears when at least one entry
is actually unclassified, same as today's pattern).

**Billing chip — deliberately irregular, not neutral.** 103-UI-SPEC §3 states the billing chip is
"neutral border color... never accent or status color (billing is identity metadata, not a state
signal)." **This document creates one narrow, explicit exception for the Unclassified case**,
because D-09's own decision text calls this "load-bearing, not cosmetic" — an unmapped vendor
silently defaulting to `api`/`normal` would suppress the expensive-model confirm exactly where
nobody has verified it's safe to. The chip must look different enough that an operator notices it's
not an ordinary billing label:

- Text: **"UNCLASSIFIED"** (full word — not abbreviated to fit the existing 3-char "API"/"SUB"
  pattern; the extra width is itself part of the signal)
- Treatment: `Badge variant="outline"` with `border-dashed border-(--status-warn)/50
  text-(--status-warn)` (dashed border matches this codebase's existing "provenance uncertain"
  convention, e.g. the retired STUB chip's dashed style; `--status-warn` because this is the one
  billing state that carries real risk — the operator cannot yet trust the cost-tier confirm gate
  for this entry)
- Still Label typography, `text-xs px-1 py-0`, matching every other chip's sizing — only the color
  and text differ.

**`costTier` for an Unclassified entry: `"unknown"` — kept from revision 1, re-confirmed correct by
the checker in both revision 2 and revision 3. Not touched again here.** `needsCostConfirm`
(`BrainPickerRow.tsx:83-85`) fires the expand-to-confirm friction for ANY row whose `costTier` is
`"expensive"` OR `"unknown"`. `normalizeGlobalCatalogueEntry` (`BrainPicker.tsx:125-134`) currently
hardcodes every entry's `costTier` to `"normal"` — its own docstring (`:114-123`) explains this was
a deliberate choice specifically to keep `needsCostConfirm` from firing on data with no real
cost-tier signal, because the pre-D-09 global axis never carried one. D-09 changes that premise for
exactly the vendors it cannot classify: an Unclassified entry, by definition, has an unverified
billing/cost profile — tagging it `"normal"` would keep the confirm gate silently suppressed for
precisely the entries D-09's own honesty clause says must NOT be silently trusted. An Unclassified
entry's `costTier` must resolve to **`"unknown"`**, never `"normal"` — this is what makes D-09's
"must never be silently defaulted" clause actually reach `needsCostConfirm`, rather than stopping at
the billing chip alone.

**Revision 2 correction (history — the diagnosis below is still accurate; the fix it proposed was
incomplete, see Revision 3 below).** Revision 1 asserted that `GlobalSwapModal`'s existing
`needsCostWarning` line "already implements" 103-UI-SPEC §3's no-stacking rule and that "the only
change this phase makes is that real data can now reach it." That was wrong. `handleActivate`
(`BrainPicker.tsx:399-416`) gated the inline expand-to-confirm on `needsCostConfirm(entry)` alone,
with no scope check anywhere in the function:

```
const handleActivate = useCallback(
  (entry: CatalogueEntry) => {
    if (expandedId === entry.id) {
      handleSelect(entry);
      setExpandedId(null);
      return;
    }
    if (needsCostConfirm(entry)) {   // scope-blind — fires at BOTH scopes

      return;
    }
    handleSelect(entry);
  },
  [expandedId, handleSelect]

```

So once `costTier: "unknown"` reaches a live entry (this phase's own change, above), a cost-tier row
at `scope === "global"` opened the row's own inline confirm first, and only THEN opened
`GlobalSwapModal`, which renders its own separate `needsCostWarning` line
(`GlobalSwapModal.tsx:475`, `:610-616`) — two friction surfaces stacked for one decision, exactly
what 103-UI-SPEC §3 forbids, and exactly what `BrainPicker.tsx:114-123`'s own docstring predicted
would happen if `costTier` were ever tagged `"unknown"` without a gate change.

**Revision 3 correction — revision 2's fix closed the KEYBOARD path only; the MOUSE path was never
touched and still stacks. This is the defect this revision fixes.** Revision 2 added
`scope !== "global"` to `BrainPicker.tsx`'s own `handleActivate`, and its text claimed this was "the
one place both input modes already share." **That claim was false, verified against the live file:**

1. **`BrainPickerRow` has its own, separate, still scope-blind local function of the same name.**
   `BrainPickerRow.tsx:124-153`:
   ```
   const needsConfirm = needsCostConfirm(entry);   // :128 — computed LOCALLY, no scope input

   const handleActivate = (event: React.MouseEvent<HTMLButtonElement>) => {   // :146
     event.stopPropagation();
     if (needsConfirm) {
       onExpandChange(true);   // :149 — expands the row's OWN inline confirm, then RETURNS
       return;
     }
     onSelect(entry);
   };
   ```
   `BrainPickerRow` has **no `scope` prop** (`grep -n "scope" src/components/brains/BrainPickerRow.tsx`
   returns one hit, a comment, and no member of `BrainPickerRowProps`) — so `:128`'s `needsConfirm`
   cannot be made scope-aware from inside this file as it stood.
2. **A mouse click fires the row's OWN `onClick` (`:178`, `onClick={handleActivate}`), not
   `BrainPicker.tsx`'s patched function.** `BrainPickerRow.tsx:140-145`'s own comment states the row
   stops event propagation specifically so a click never ALSO reaches cmdk's bubbled `CommandItem`
   select path — "without this, a single click would double-fire `handleActivate`." So on the FIRST
   activation, the mouse path provably never reaches `BrainPicker.tsx`'s patched, scope-aware
   `handleActivate` at all.
3. **The second click (`Confirm swap`, `BrainPickerRow.tsx:155-159`) does reach
   `BrainPicker.tsx`'s `handleActivate` — via `onSelect(entry)`, wired at `BrainPicker.tsx:565`
   (`onSelect={handleActivate}`) — but by then `expandedId === entry.id` is already true, so it
   takes the FIRST branch (`:437-440`, `handleSelect(entry); setExpandedId(null); return;`) and the
   `scope !== "global"` condition is never evaluated at all.**

Net effect: at "All profiles" scope with `costTier: "unknown"`, a mouse user still sees the row's
inline expand-to-confirm (`BrainPickerRow.tsx:216-235`) AND then `GlobalSwapModal`'s own warning
line — the stacking defect persists for that input path. **Revision 2 also made input-mode parity
strictly worse than before**: keyboard and mouse were previously consistently wrong (both
scope-blind); revision 2 fixed keyboard only, so the two paths now disagree — exactly the property
`BrainPicker.tsx:389-396` documents as a guarantee (103-11/CR-02) and revision 2 claimed, incorrectly,
to preserve.

**Two sentences from revision 2 are retracted as false, not merely superseded:**
- *"`handleActivate` stays the single function `CommandItem.onSelect` (keyboard) and
  `BrainPickerRow`'s own button (mouse) both call, so the two input modes cannot drift apart"* —
  false. The row's button calls the row's OWN local `handleActivate`, which returns at `:149`
  without ever invoking `BrainPicker.tsx`'s function when a confirm is needed.
- *"No change is needed inside `BrainPickerRow.tsx` itself: its `isExpanded` prop is fully
  controlled by `BrainPicker`'s `expandedId` state"* — false in the way that matters. `expandedId`
  is set **at the row's own request**, via `onExpandChange(true)` from a scope-blind local
  computation the picker's gate never sees. `BrainPickerRow.tsx` IS a modified file this phase.

**Required fix: hoist the scope-aware gate into `BrainPicker`, computed exactly once, and pass it
into `BrainPickerRow` as a new prop — so both input modes read the same value instead of each
computing their own.**

In `BrainPicker.tsx`, one shared, scope-aware predicate (memoized on `scope`, reusing the already-
imported `needsCostConfirm`):

```
const shouldConfirmCost = useCallback(
  (entry: CatalogueEntry) => scope !== "global" && needsCostConfirm(entry),
  [scope]
);
```

Consumed at BOTH sites in `BrainPicker.tsx` — the row-rendering loop and `handleActivate` — so
there is exactly one formula, not two that happen to agree:

```
// Row rendering (BrainPicker.tsx, inside the group.entries.map()):
<BrainPickerRow
  entry={entry}
  needsConfirm={shouldConfirmCost(entry)}   // NEW prop — see below
  isCurrent={...}
  isExpanded={expandedId === entry.id}
  onExpandChange={(exp) => setExpandedId(exp ? entry.id : null)}
  onSelect={handleActivate}
/>

// handleActivate (BrainPicker.tsx:399-416), keyboard path:
const handleActivate = useCallback(
  (entry: CatalogueEntry) => {
    if (expandedId === entry.id) {
      handleSelect(entry);
      setExpandedId(null);
      return;
    }
    if (shouldConfirmCost(entry)) {
      setExpandedId(entry.id);
      return;
    }
    handleSelect(entry);
  },
  [expandedId, handleSelect, shouldConfirmCost]
);
```

In `BrainPickerRow.tsx`, add `needsConfirm: boolean` to `BrainPickerRowProps` and **delete the local
computation at `:128`** — the row stops importing/calling `needsCostConfirm` for this purpose and
reads the prop instead. Its existing two consumers of `needsConfirm` are otherwise untouched — the
mouse-path gate (`:148`, `if (needsConfirm) { onExpandChange(true); return; }`) and the JSX render
gate (`:216`, `isExpanded && needsConfirm`) both now read the value `BrainPicker` computed once, so a
mouse click and a keyboard activation on the same row can no longer disagree about whether a confirm
step is needed. `needsCostConfirm(entry)` itself (`BrainPickerRow.tsx:83-85`) is **unchanged and
still exported** — it remains the pure, scope-independent "is this entry cost-sensitive at all"
predicate; `shouldConfirmCost` is the new, additional, scope-aware wrapper that decides whether THIS
picker instance should act on that predicate right now. `BrainPickerRow.tsx` is confirmed a modified
file this phase — retracting revision 2's claim otherwise.

**Resulting contract, stated per scope AND per input path — exactly one friction surface each,
identically for mouse and keyboard:**

- **"This profile" scope:** the row's own inline expand-to-confirm (103-UI-SPEC §3/§11,
  `BrainPickerRow.tsx:216-235`) is the ONLY friction, on both a mouse click and a keyboard
  activation. Unchanged from 103-UI-SPEC — there is no modal on this path, so there was never a
  second surface to stack against.
- **"All profiles" scope:** the inline expand-to-confirm **never appears, on either input path** —
  `needsConfirm` is `false` for every row regardless of `costTier`, so both
  `BrainPickerRow`'s own mouse-path gate and `BrainPicker`'s keyboard-path gate dispatch straight to
  `handleSelect(entry)` / `onSelect(entry)`, which opens `GlobalSwapModal`. That modal's existing
  `needsCostWarning` line (`GlobalSwapModal.tsx:475`, `:610-616`, "This model may be expensive per
  token — N profiles will be switched to it.") is the ONLY friction. No new copy or component — the
  fix is purely which of two already-specified surfaces is reachable, and it is now reachable
  identically regardless of how the row was activated.

**Parity is now the property most at risk, and it is worth a test.** The codebase already treats
mouse/keyboard confirm-branch parity as a guarantee (`BrainPicker.tsx:389-396`, tagged 103-11/CR-02)
— that comment was true for the *pre-D-09* code (where both paths independently called the same
scope-blind `needsCostConfirm(entry)` and happened to agree only because neither path considered
scope) and would have stayed silently false under revision 2's fix (where the two paths would have
started calling two DIFFERENT conditions). The planner should carry a test asserting mouse-path and
keyboard-path outcomes agree for every (scope, costTier) combination — not a test of either path in
isolation, which cannot detect this class of defect (both revision 1 and revision 2 would have
looked fine under a single-path test).

This closes the collision `109-CONTEXT.md`'s own Discretion list named directly ("D-09's cost-tier
restoration interacts with" the cost-tier confirm) — it was named as a risk at scoping time and this
section is where it gets resolved, not deferred further.

**Engineering note (non-blocking, flagged so the planner doesn't re-inherit a live bug from a
citation alone):** `109-CONTEXT.md` cites `PROVIDER_BILLING`/`getBillingType` as D-09's data
source, but `getBillingType` (`src/lib/providers.ts:32-35`) itself silently defaults an unmapped
provider to `"api"` (`?? "api"`, its own comment says "conservative") — calling this function to
*detect* whether a vendor is unclassified would always return `"api"` and could never produce the
Unclassified group at all. Unmapped-vendor detection must test membership in `PROVIDER_BILLING`
directly (e.g. `vendorKey in PROVIDER_BILLING`), never rely on `getBillingType()`'s return value for
that decision. `getBillingType()` remains fine to use AFTER a vendor is confirmed mapped, for
resolving which of Subscription/API it belongs to.

**What this document does not decide:** the `vendor` → `PROVIDER_BILLING` key mapping itself (e.g.
catalogue `"anthropic"` → registry key `anthropic_direct`) and what counts as "Local" for Ollama are
both named as Claude's Discretion in `109-CONTEXT.md` and are engineering/data-shape questions, not
visual ones — the planner resolves them. This section only specifies what the UI does once an entry
is genuinely unclassified: render it honestly, in its own group, with a chip that looks different on
purpose, a `costTier` that keeps the cost-tier confirm gate honest, and a single, scope-appropriate
friction surface — identical for mouse and keyboard — when that confirm gate fires.

### §G. Pre-swap confirm modal's current-engine column (D-06 fix + `"Auto"` retirement)

**Success criterion 1 names this surface explicitly.** `GlobalSwapModal`'s confirm-phase row list
(`GlobalSwapModal.tsx:617-628`, `[ProfileName] [CurrentEngineDisplayName] → [NewEngineDisplayName]`)
renders `p.currentModelDisplayName` (`GlobalSwapModal.tsx:624`), sourced from `BrainPicker.tsx`'s
`globalSwapProfiles` memo (`:347-372`).

**Corrected in revision 1 (2026-08-07), confirmed fully resolved on re-check in revision 2 — do not
re-open. Untouched in revision 3.** The checker found that the first draft of this section named the
wrong line as the render-blocking defect, and a planner following that earlier text literally would
have left the real bug on screen. The corrected mechanism, verified against the live file, is below —
three distinct points, kept separate on purpose so the fix and the two other consumers are not
conflated:

1. **Precedence (D-06).** `const engine = activeEngines[p.profileId] ?? null;` (`:349`) reads only
   the per-profile *telemetry* rung — it never sees a live per-profile *override* (§B's new top
   rung). A profile that was just pinned will show its pre-pin engine in this column until the next
   telemetry resolution, even though `swap.state` already knows the truth. The fix: derive
   `currentModel`/`currentModelDisplayName` for each row through the same full precedence chain
   `useResolvedBrain(profileId)` exposes, not a raw `activeEngines` lookup.

2. **The rendered `"Auto"` literal — the actual on-screen defect, corrected here.**
   `currentModelDisplayName` is computed by the ternary at `BrainPicker.tsx:358-360`:
   ```
   currentModelDisplayName: engine
     ? resolveModelDisplayName(currentModel, entries)
     : "Auto",
   ```
   `resolveModelDisplayName` only runs in the TRUE branch, where `engine` (and therefore
   `currentModel`) is always a real, resolved model id — it can never be called with a placeholder.
   In the no-telemetry case this section exists to fix, the ternary takes the FALSE branch and
   renders the capitalized literal `"Auto"` directly, with no `resolveModelDisplayName` call
   involved at all. **This is the value that reaches the screen** — `GlobalSwapModal.tsx:624`
   renders `p.currentModelDisplayName` unmodified. **The fix: change the ternary's false branch from
   `"Auto"` to §A's canonical `"Not reported"` string.**

3. **A separate, related value — flagged for the planner, not required by this fix. Checker-traced
   in revision 2: neither consumer is user-visible, so this stays correctly flagged as a follow-up,
   not upgraded to a requirement.** `currentModel` itself (`BrainPicker.tsx:350`,
   `const currentModel = engine?.model ?? "auto";` — lowercase, a genuinely different value from
   #2's capitalized `"Auto"`) is **not** what renders in the confirm-row list. It does feed two
   other consumers: `SnapshotEntry.model` (captured into the post-swap result snapshot,
   `GlobalSwapModal.tsx:481`) and the prior-override display-name lookup
   (`snap.find((s) => s.model === modelOverride)`, `GlobalSwapModal.tsx:502`). Whether this
   lowercase `"auto"` sentinel also needs replacing at those two sites is a real, open question this
   document does not resolve — neither is the criterion-1 confirm-row defect, and conflating this
   value with #2 would misattribute two different bugs with two different consumers to one fix.
   Flagged here explicitly as a candidate follow-up, not folded into this section's required fix.

**Visual consequence: none beyond §A/§B.** The row list's existing anatomy (name / current /
arrow / target, `Pin` icon for `hasConfiguredDefault`) is unchanged — only the values feeding
`currentModel`/`currentModelDisplayName` change, and `"Not reported"` renders in that slot exactly
as it would in the badge or Settings row (italic, muted, no fabricated identifier).

**Explicitly flagged as uncertain, per this document's own honesty mandate:** whether the existing
config-only `hasConfiguredDefault`/`Pin` icon (103-17's design, unchanged) should ALSO fire for a
profile whose *current* column is now sourced from the override rung is not answered here — the two
signals mean different things (a saved config preference vs. a live runtime pin) and conflating them
into one icon risks asserting something the system doesn't distinguish. This document keeps them
separate and unchanged; if the planner finds this reads ambiguously once built, treat it as a
follow-up rather than silently overloading the existing Pin icon's meaning.

### §H. Settings swap-history section (D-10/D-11/D-12) — the new surface

**Host:** directly under each existing per-profile row (`Settings.tsx:256-339`), full width of that
row's container, indented `md` (16px) to read as the row's own child content rather than a sibling
row.

**Component:** compose `Collapsible` / `CollapsibleTrigger` / `CollapsibleContent`
(`src/components/ui/collapsible.tsx` — installed, unused elsewhere in this codebase; this is its
first consumer). Do not hand-roll a show/hide `useState` toggle — the primitive exists precisely for
this.

**Default state: collapsed.** With up to several profiles each carrying their own history section,
defaulting to expanded would make the Settings page unusably long on first load. This mirrors the
audit-trail convention (reveal on demand) already established by 103-UI-SPEC's own result-state
disclosure pattern.

**Trigger row anatomy** (Label typography, `--muted-foreground` idle / `--foreground` on
hover-open, matching existing Settings row interactive-text conventions):

```
[ChevronRight/ChevronDown, 12px, rotates on open] [History icon, 12px] "Swap history" [count badge]
```

- Chevron: `ChevronRight` collapsed, `ChevronDown` expanded (Lucide, matches the existing
  expand/collapse idiom already used in this codebase, e.g. `Chat.tsx`'s `ChevronDown` on the
  composer pill).
- `History` icon (Lucide) — new icon import for this codebase's brain surfaces, chosen because it
  is the one Lucide icon whose name unambiguously matches the section's content and is not already
  overloaded by an adjacent meaning in this file (`Clock` already means "session override" here).
- Count badge: the REAL combined row count (per-profile + global, post-merge, pre-truncation) —
  e.g. "Swap history (12)". Never a rounded or capped-looking number; if the true count exceeds the
  display cap, the badge still shows the true count (e.g. "(37)") while the expanded content shows
  the truncation caption below — the badge and the caption together tell the whole honest story
  (there are 37, we're showing the most recent {DISPLAY_CAP}).

`SwapHistorySection` row shape (`GlobalSwapModal.tsx:298-323`) exactly, with one addition:


- Outcome icon / label: unchanged, reuse `describeSwapOutcome` (`useControlVerbSwaps.ts:90-108`) —
  already decided, do not re-derive (per this document's instructions).
- `GLOBAL` badge: `Badge variant="outline" className="text-xs uppercase px-1 py-0"` reading
  "GLOBAL" — same treatment as the header badge's existing "Global" chip
  (`BrainHeaderBadge.tsx:172-179`). Rendered only on rows sourced from the new `listGlobal` query
  (D-11); per-profile-sourced rows carry no badge (absence of the badge IS the "this profile's own
  swap" signal — no second badge needed for the common case).
- No new icon vocabulary — the existing 3-icon set (Check/X/AlertTriangle) from
  `SwapHistorySection` covers every outcome; this section does not need a 4th.

**Pinned note (D-12), live-state-derived:** when the profile currently holds its own override
(read from the same live `swap.state` signal §B's `override` rung uses — never reconstructed from
the history rows themselves, per the decision's explicit prohibition), render one note **above the

The note appears only while the pin is genuinely active; it disappears the moment the override is
cleared, with no separate "was pinned as of {row's time}" retrospective claim (the decision

**Empty state** (both queries return zero rows for this profile):

**Truncation caption** — reuses the existing display-cap mechanism (`SWAP_HISTORY_CAP = 20`,
