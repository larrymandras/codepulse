<objective>
Restore genuine grouping and billing metadata to the picker from CodePulse's own provider registry,
add the honest "Unclassified" group, and — because tagging an entry `costTier: "unknown"` makes the
expensive-model confirm fire for the first time — fix the confirm-gate collision it exposes, on
BOTH input paths.

Purpose: the single live catalogue returns only `id`/`name`/`vendor`, so today's adapter flattens
every entry to `group`/`billing: "api"`, `costTier: "normal"` — collapsing the Subscription/API/Local
grouping and disabling the cost-tier confirm entirely. Restoring the confirm is the point; the
side effect is that it now stacks with the global modal's own warning line, which 103-UI-SPEC
section 3 forbids.
Output: one vendor mapper, a fourth picker group, and one scope-aware confirm gate consumed
identically by mouse and keyboard.

**D-13 is a locked decision that CORRECTS D-09's stated premise. Implement D-13's rule.**

D-09's text assumed a roughly 1:1 alias table ("the catalogue reports `anthropic`, the registry
keys are `anthropic_direct`"). Research falsified that premise, verified live:

- `swap.catalogue`'s `vendor` means MODEL MANUFACTURER. The static pinned Claude tier hardcodes
  `"vendor": "anthropic"` (`ws_commands.py:1202`); every dynamic entry sets
  `"vendor": model_id.split("/", 1)[0]` (`:1225`) — an OpenRouter routing slug like `google`,
  `x-ai`, `meta-llama`, `mistralai`, `deepseek`, `qwen`. Anthropic-native OpenRouter listings are
  excluded (`:1223-1224`) to avoid duplicating the pinned tier.
- `PROVIDER_BILLING`'s keys mean EXECUTION/BILLING CHANNEL: `anthropic_direct`, `openrouter`,
  `ollama`, `claude-cli`, `codex`, `antigravity`, `claude-sdk` (`src/lib/providers.ts:22-29`).
- These are different axes. A literal `vendor in PROVIDER_BILLING` lookup matches NOTHING — not
  even the Claude tier — and would put essentially the entire live catalogue (300+ entries) in
  "Unclassified", firing the expensive-model confirm on almost every row. That lands close to the
  flattening D-09 exists to undo, which is why D-13 rejects it.

**D-13's rule, verbatim:** map `"anthropic"` to `anthropic_direct`; every other non-empty vendor
reaching this catalogue arrived via `swap_model._openrouter.get_models()`
(`ws_commands.py:1206-1238` — verified, there is no third source) and is therefore billed
per-token as `api`. **D-09's honesty clause survives unchanged:** an empty or missing vendor
renders in the explicit "Unclassified" group and is never silently defaulted to `api`.

**D-13's stated consequence, to be shown on screen and not hidden:** the Subscription and Local
groups are structurally unreachable from `swap.catalogue` today — `grep -in "ollama"` across
`swap_model.py` and `ws_commands.py` returns zero hits and no CLI-gateway provider appears — so
they render empty via the existing `.filter((g) => g.entries.length > 0)` and simply do not appear.
That is honest: it matches what the server can actually report. Populating them is the already-
deferred `swap.catalogue` enrichment, not this phase.

**Non-blocking engineering trap, verified:** `getBillingType` (`src/lib/providers.ts:32-35`)
silently defaults an unmapped provider to `"api"` (`?? "api"`, its own comment says
"conservative"). Calling it to DETECT whether a vendor is unclassified would always return `"api"`
and could never produce the Unclassified group. Unmapped detection must test membership in
`PROVIDER_BILLING` directly. `getBillingType()` is fine to use AFTER a vendor is confirmed mapped.

**UI-SPEC section F's confirm-gate fix — read the mechanism carefully, two earlier revisions of
this fix were wrong:**

1. `BrainPickerRow` has its OWN local `handleActivate` and computes `needsConfirm =
   needsCostConfirm(entry)` locally at `:128`, with NO `scope` prop available to it.
2. A mouse click fires the row's own `onClick={handleActivate}` (`:178`), which returns at `:149`
   after `onExpandChange(true)` — it provably never reaches `BrainPicker.tsx`'s `handleActivate`
   on a first activation. The row stops propagation deliberately (`:140-145`) so a click cannot
   double-fire.
3. The second click ("Confirm swap", `:155-159`) DOES reach `BrainPicker.tsx`'s `handleActivate`
   via `onSelect(entry)` (`BrainPicker.tsx:565`), but by then `expandedId === entry.id`, so it
   takes the first branch and returns before any scope condition is evaluated.

So patching only `BrainPicker.tsx`'s `handleActivate` fixes the keyboard path and leaves the mouse
path stacking — and makes the two paths DISAGREE, breaking the mouse/keyboard parity
`BrainPicker.tsx:389-396` documents as a guarantee (103-11/CR-02).

**The required shape** (UI-SPEC section F, revision 3):

```
// BrainPicker.tsx — one formula, memoized on scope
const shouldConfirmCost = useCallback(
  (entry: CatalogueEntry) => scope !== "global" && needsCostConfirm(entry),
  [scope]
);
```
consumed at BOTH sites in `BrainPicker.tsx` — the row-rendering loop
(`needsConfirm={shouldConfirmCost(entry)}`) and `handleActivate` — and consumed in
`BrainPickerRow.tsx` as a new required `needsConfirm: boolean` prop that REPLACES its local
`needsCostConfirm(entry)` call. `needsCostConfirm` itself stays exported and unchanged — it remains
the pure, scope-independent "is this entry cost-sensitive at all" predicate.

**Resulting contract, per scope AND per input path — exactly one friction surface each:**
- "This profile" scope: the row's inline expand-to-confirm is the ONLY friction, on both paths.
- "All profiles" scope: the inline expand-to-confirm NEVER appears on either path; the global
  modal's existing `needsCostWarning` line (`GlobalSwapModal.tsx:475`, `:610-616`) is the only
  friction.
