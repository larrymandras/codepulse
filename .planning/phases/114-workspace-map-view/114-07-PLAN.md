    - `.planning/phases/114-workspace-map-view/114-RESEARCH.md` § "Pitfall 1: `fx`/`fy` without the

      count, traversing the adjacency map top-down rather than filtering the flat 4,912-row array.
  </read_first>
  <files>src/lib/workspaceMapLayout.ts</files>
  <action>
    Implement `layoutNodes(tree, rollups, expandedSet, options?)` returning `{ nodes, links }`, still
    with zero React/Convex imports.

    **Visibility rule.** The function takes a `visibleDepth` floor of **2** (departments and roots
    always visible, plus every root's depth-1 children) and descends further only into nodes whose
    `nodeKey` is present in `expandedSet`. This is what makes D-01's 391-node first paint need no
    clicks — the default visible set is a floor, not an empty `expandedSet`. Traverse **top-down
    through the adjacency map**; never `dirs.filter(...)` over the flat array (RESEARCH.md § Pattern 4
    names that as the anti-pattern, and the adjacency map from plan 114-05 exists precisely to avoid it).

    **Rings** (radii in `react-force-graph-2d`'s arbitrary force-space units, the same space
    `ForceGraphCanvas`'s existing `clusterForce` uses — not CSS pixels; `zoomToFit` handles screen
    fitting):
    - ring 0 — center hub, radius 0
    - ring 1 — the 4 department hubs, radius 140
    - ring 2 — root hubs, radius 300
    - ring 3 — depth-1 directories, radius 460
    - ring 4+ — depth d directories at `460 + 130 * (d - 1)`

    **Angular allocation:**
    - Each **department** gets a sector proportional to its total directory count, ordered by
      descending count starting at 12 o'clock going clockwise, with an **8° minimum floor** per
      department (non-binding on today's data — the smallest department is already ~40.7° — but
      protective if the mix shifts).
    - Each **root** gets a sub-sector within its department proportional to **√(root's directory
      count)**, not the linear count, with a **1.5° minimum floor** per root. The sqrt is the direct
      answer to the dataset's lopsidedness: two roots hold 1,041 and 601 directories while 19 roots
      hold ten or fewer, so a linear allocation would crowd the small roots into unclickable slivers
      while a 4×-bigger root would take 4× the width instead of 2×.
    - **Directory children at any depth** split their parent's own allocated sector **evenly** among
      currently-visible siblings — never weighted by size. Node size already encodes rolled-up scale
      (D-07); weighting angle too would double-encode the same signal.

    **Collision handling, index-based and fully deterministic:** when a ring position's per-node arc
    length would fall below ~14 force-space units (the minimum click-target width at typical
    post-`zoomToFit` scale), stagger alternating siblings — even-indexed siblings at the ring's
    primary radius, odd-indexed at `primary + 65` (half the standard 130 per-depth increment). Index-
    based, never force-based, so it stays reproducible and screenshot-testable exactly like the
    primary layout.

    **Node size (`val`), sqrt-scaled from rolled-up file count:**
    - center hub: 14 (fixed) · department hub: 10 (fixed)
    - root hub: `5 + 5 * √(rolledUpFiles / maxRootRolledUpFiles)` → range 5–10
    - directory, any depth: `2 + 4 * √(rolledUpFiles / maxDirRolledUpFiles)` → range 2–6 (2 matches
      `ForceGraphCanvas`'s own floor, `Math.max(node.val ?? 3, 2)` at `:226` and `:269`)

    `maxRootRolledUpFiles` and `maxDirRolledUpFiles` are computed **once from the supplied data**, never
    hardcoded, so the scale stays correct as the tree changes. Guard division by zero (a payload where
    every rolled-up count is 0 must yield the floor value, not `NaN`).

    **The pitfall that will silently half-work if you skip it.** Every returned node must carry
    `fx`/`fy` **and** a plain `x`/`y` mirror, assigned in a dedicated final pass over the whole nodes
    array after all positions are computed — `n.x = n.fx; n.y = n.fy;` (2D, no `z`), exactly
    `skillVault.ts:382-388`. `fx`/`fy` alone only pins the simulation; d3-force still assigns an
    initial `x`/`y` internally on first tick unless one is present, and at `cooldownTicks={0}` there
    is no tick budget for that correction before the first paint. Setting only `fx`/`fy` **will pass a
    casual visual check** and fail on the first frame. Do the mirror pass.

    **Links:** parent→child edges only (center→department, department→root, root→depth-1, and each
    expanded parent→child). No cross-links, no department- or access-colored link encoding — fill,
    halo and size are already three channels and a fourth would be noise across 391+ edges.

    Carry each node's `department`, `access`, `rootId`, `dirPath`, `nodeKey`, `depth`, a `kind`
    discriminator (`"center" | "department" | "root" | "dir"`), its direct counts and its rolled-up
    counts, so the canvas and the side panel can read everything they need off the node without
    re-joining against the payload.

    **Hub aggregates — this function is their sole producer.** A `department` hub node carries
    `dirCount` = that department's total directory count, and `rolled` = the element-wise sum of its
    member roots' rolled-up `RollupTotals` (`fileCount`, `totalSize`, `withheldCount`). The directory
    count is the **same figure the angular allocation above already computes** for that department's
    proportional sector — compute it once and read it in both places, never twice. The `center` hub
    carries the whole-payload equivalents. Populate `dirCount` on `root` and `dir` nodes too (subtree
    directory rows, itself included) so no node ships it `undefined`. Do **not** try to key these
    aggregates into `computeRollups`' `RollupMap`: that map is keyed `${rootId}|${dirPath}` and a
    department has neither, which is precisely why the aggregate belongs here. Plan 114-08's hub
    panel reads `node.dirCount` and `node.rolled.fileCount` off the node and computes nothing itself.

    **Suite "determinism" (D-08).** Two levels of proof, both required:

    1. **Repeat-call:** call `layoutNodes` twice on identical inputs and `toEqual` the full
       `{ nodes, links }` including `fx`, `fy`, `x`, `y` and `val` on every node.
    2. **Order-independence — this is the one that matters:** feed the same `dirs` through
       `buildTree` + `computeRollups` + `layoutNodes` twice, once in forward order and once as
       `dirs.slice().reverse()`, and assert the two `{ nodes, links }` results are deep-equal after
       sorting both node arrays by `nodeKey`. A same-reference-twice test proves nothing about this
       property — it would pass against an implementation whose angles depend on iteration order, and
       iteration order is exactly what a Convex payload does not guarantee. Comment that reasoning in
       the test so nobody later "simplifies" it back to the weaker form.

    Also assert, in the same suite:
    - Every node has `x === fx` and `y === fy` — the mirror pass, checked on the output rather than
      by grepping the source, since the source grep in Task 1 cannot prove the pass ran for every node.
    - No node has `fx`, `fy`, `x` or `y` equal to `undefined` or `NaN`.

    **Suite "sizing" (D-07 / D-05).** Assert:
    - `kind === "center"` has `val === 14`; every `kind === "department"` has `val === 10`.
    - Root hub `val` values fall within `[5, 10]` inclusive; directory `val` values within `[2, 6]`.
    - The root with the **largest** rolled-up file count has the largest root `val`, and the root with
      the smallest has the smallest — the ordering property, which is what D-07 actually asserts
      ("node size encodes rolled-up file count"); a range check alone would pass for a constant.
    - Radii are correct per ring: assert `Math.hypot(x, y)` is 0 for the center, ~140 for departments,
      ~300 for roots and ~460 for depth-1 directories — with a tolerance that accommodates the
      collision stagger's `+65` secondary radius where it applies.
    - A degenerate input where every rolled-up file count is 0 yields floor `val`s and no `NaN`.
