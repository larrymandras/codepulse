<planner_corrections>
**1. Why a backfill is needed at all, stated so it is not mistaken for scope creep.** Plan 126-02
retired the entity-row writes, so the version that is active on the live deployment at deploy time
was written by the OLD writer: it has ~6,591 entity rows and ZERO chunk rows. Without a backfill,
`/tool-galaxy` goes from an error card to an empty-state explainer and stays there until Ástríðr's
nightly `graph:snapshot` cron next runs — and Phase 126's criterion 1 requires that page to render
its real content against live data, asserted on a node count. Triggering the cross-repo producer on
demand is an assumption about `astridr-repo` that nothing in this phase's artifacts supports, so the
backfill removes the dependency instead of betting on it.

**2. The backfill reuses the real writer rather than re-implementing chunking.** An action pages the
existing entity rows out through a bounded internal query, reconstructs `upsertGraphSnapshot`'s
argument object from the meta doc plus those rows, and calls the REAL production mutation. That means
the backfill cannot drift from the writer, and it exercises the exact code path plan 126-02 built. It
creates a new version, which is correct: the sweep already drains old ones.

**3. Throw `ConvexError`, never a plain `Error`.** CLAUDE.md records that Convex redacts plain
`Error` messages to "Server Error" client-side, while `ConvexError`'s `.data` survives. A completeness
failure that reaches the operator as "Server Error" is indistinguishable from the timeout this phase
is fixing, which would make the fix look like it did not work.

**4. Bound the chunk read too.** Replacing `.collect()` with another unbounded read just moves the
cliff. Use `.take(GRAPH_BLOB_MAX_CHUNKS + 1)` on a module constant and treat the extra row as the
signal, mirroring `convex/graphSnapshots.ts:252-259`'s existing idiom in this same file.

**5. Belt AND braces on ordering, deliberately.** Query `by_snapshot_version_seq` with `.order("asc")`
— because the index key literally ends in `seq`, ascending IS seq-ascending — AND rejoin through
`joinGraphBlobChunks`, which sorts on `seq` again. That redundancy is not sloppiness: it is what makes
the ordering test in plan 126-08 able to seed a fixture whose insertion order differs from `seq` order
and still assert a correct reassembly. `126-CONTEXT.md` records that nothing in this repo currently
tests reassembly order and that the one comment claiming it is a claim, not evidence.

**6. Do not "improve" the sampling story here.** The stored graph is already truncated upstream
(71,016 nodes emitted for `astridr-repo`, 1,500 stored). `sources[].truncated`, `nodeCount` and
`storedNodeCount` already carry that fact through the return contract; keep all three flowing
unchanged. Whether the UI should present a sampled graph differently is explicitly a DEFERRED idea in
`126-CONTEXT.md`, not this phase's work.
