<planner_corrections>
**The remedy choice D-09 left to Claude's discretion, settled here: guard the parser, do not build a
cron-string generator.** D-09 offered two defensible shapes and said "the second is smaller and the
first is only worth it if a genuine cron string is needed elsewhere." Deriving real cron expressions
from `intervalSeconds`/`dailyUTC` was rejected for a reason that only shows up on inspection of
`cronToHuman` itself: `"Every 5 min"` would become `*/5 * * * *`, and `cronToHuman.ts:16-22` has no
step-syntax branch — `min === "*/5"` fails the `min === "*"` test and falls through to
`Every hour at minute */5`. So option one does not actually fix the display without ALSO extending
the parser, which is net-new logic with no analog in this codebase (`126-PATTERNS.md` records
exactly that: "no analog — new logic").

The fix is therefore: `CronJobList` runs the cron parser only when the string it holds is actually a
cron expression, using the `isValidCron()` helper that already exists and is already exported from
the same module as `cronToHuman()`. Non-cron rows render their schedule ONCE, as the readable label
it always was. Real cron rows — the ones `CronSheet`'s `FREQUENCY_TO_CRON` produces via
`handleSave`/`cron.create` — keep today's expression-plus-gloss rendering, which is what the positive
control in Task 1's test proves.

**What is deliberately NOT fixed, and why, so it is not read as an oversight:** the root naming
defect is that `Automation.tsx:41-44` assigns a human label into a field called `expression`, and the
same field is handed to `CronSheet` (`CronSheet.tsx:12-13,31`) as `initialExpression` when a row is
clicked. Re-shaping `CronJob` so the label and the machine expression are separate fields would
change the edit/save path, which dispatches `cron.trigger`/`cron.create` to Ástríðr — net-new UI and
cross-repo behaviour inside a defect sweep. Record it as a follow-up in the SUMMARY; do not build it
here.
</planner_corrections>
