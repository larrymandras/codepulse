<planner_corrections>
**1. The read-cost fixture size is load-bearing and is an acceptance criterion, not a detail.** Size
the fixture like the real data: a serialized blob whose length forces the same order of chunk count
the live graph would produce (D-06-REVISED measured ~1.03 MB total, i.e. roughly 9 chunks at
`GRAPH_BLOB_CHUNK_CHARS = 128_000`). A 3-chunk toy fixture would pass against almost anything. State
the blob length and the chunk count you used.

**2. The read-cost assertion needs the OLD number beside it to mean anything.** Assert
`readCount()` is small (roughly meta + chunk count), and state in the same test's comment what the
pre-change path would have read for the same graph: 6,591 rows (4,001 nodes + 2,590 links, D-05's
live measurement) against a 4,096-read ceiling. A bare `toBeLessThan(10)` with no reference figure is
a number with no meaning attached.

**3. The ordering fixture must SEPARATE insertion order from `seq` order.** Seed the fake table so
that the array/insertion order and the `seq` field disagree — e.g. insert `seq` 3,1,4,0,2. If your
fixture happens to insert them in `seq` order, the test passes against a reader that sorts by
creation time, which is the precise defect the PRECEDENT QUALIFIED note was written to prevent
someone copying from `listJobLogs`.

**4. Two DIFFERENT failure modes must be distinguished, not merged.** Out-of-order chunks must
REASSEMBLE CORRECTLY (the reader sorts). A missing `seq` must FAIL LOUDLY with a named
`ConvexError`. These are opposite expectations on superficially similar fixtures and each needs its
own test.

**5. Assert on `ConvexError`'s `.data`, not on a message match.** Plan 126-05 throws `ConvexError`
specifically because Convex redacts plain `Error` messages to "Server Error" client-side. A test that
only checks "it threw" would pass equally against a plain `Error` and would silently permit the
regression back to an unreadable failure.
</planner_corrections>
