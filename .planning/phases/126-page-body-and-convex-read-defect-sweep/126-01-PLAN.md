<planner_corrections>
**1. The filter placement question `126-PATTERNS.md` left open is RESOLVED here: no `.filter()`.**
PATTERNS flagged that `listHeldUnackedHandler` filters `ackedAt === undefined` AFTER an unbounded
`.collect()`, and asked whether the new count query should filter before or after `.take(CAP+1)`.
Filter BEFORE the take and the scan runs until it accumulates CAP+1 *matching* rows — so the number
of rows actually read depends on the acked:unacked ratio in the table, not on the cap. That is not a
bounded read; it is a read whose bound moves with data this phase does not control (Phase 127's
janitors are what will start creating acked held rows). Take CAP+1 rows with NO filter, then count
`ackedAt === undefined` in JavaScript. Reads are then exactly `min(heldRows, CAP+1)`, always.

The cost of that choice, stated rather than hidden: if held rows ever exceed CAP, `count` becomes
the unacked count *within the newest CAP held rows* — a floor. That is precisely what `truncated`
announces, and D-04 sets CAP high enough (2000 vs 46 live) that it does not bind in normal operation.

**2. Use the `take(CAP + 1)` / `length > CAP` truncation idiom, not `alerts.ts`'s `length === CAP`.**
`convex/alerts.ts:131` uses `.take(CAP)` + `truncated: active.length === CAP`, which reports `true`
on a table holding EXACTLY CAP rows — a false positive. D-04 makes `truncated` load-bearing for a
number rendered on `/inbox`, so it must be strictly correct. The stronger idiom already exists in
this repo at `convex/graphSnapshots.ts:252-259`: take CAP+1, and the extra row IS the signal.

**3. Do not "harden" this into an `internalQuery` or add a `ctx.auth` check.** Per CLAUDE.md's
SEED-008 record, gating one module's functions in isolation is the shape that was explicitly
REJECTED (215 public mutations, 85 files with no `ctx.auth`; the tailnet plus the LAN firewall block
is the boundary). The correct response to unauthenticated reachability here is bounding the query's
COST, which is what this plan does.
</planner_corrections>
