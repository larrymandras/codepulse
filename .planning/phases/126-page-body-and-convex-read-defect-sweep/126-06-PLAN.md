<objective>
Make the sidebar badge and the `/inbox` Held tab stop contradicting each other, and make every other
tab admit when its number is a floor.

Purpose: SWEEP-01's client half and SWEEP-03. The operator's screenshot showed **sidebar 46** and

page derives its tabs from a 200-row `listAll` window against a 2,777-row table, so only 9 held rows
fall inside it. D-01 and D-02 chose the remedy: the capped numbers declare their cap, and the Held tab
in particular shows a precise "N of M" because the true M already exists in the client for free.
Output: a badge reading a bounded count, tabs that say what they are, and a test that reads both
numbers in one state.
</objective>

<planner_corrections>
**1. The page's "of M" comes from `countHeldUnacked`, not `listHeldUnacked`.** `126-PATTERNS.md`
recommends the page subscribe to `listHeldUnacked` on the reasoning that the shell already subscribes
to it, so Convex's subscription dedup makes it free. That reasoning was true when it was written and
is FALSE after D-03: this plan's first task removes the shell's `listHeldUnacked` subscription. The
page would then be the ONLY subscriber to an unbounded `.collect()` — reintroducing on `/inbox`
exactly the shape SWEEP-01 removes from every route. D-04 already resolves it: "the badge's count must
remain TRUE, not merely bounded — its `truncated` flag is what D-02's display consumes." The page and
the badge read the SAME bounded query, which is what makes the dedup argument hold and what makes the
two numbers structurally incapable of disagreeing.

**2. Do not mirror `DEFAULT_LIST_ALL_LIMIT` into the client.** `listAll` accepts an optional `limit`.
Have the page declare its OWN module constant and pass it explicitly, then derive the generic marker
from `rows.length === <that same constant>`. The cap the page asserts is then the cap the page asked
for, so the two cannot drift, and no value is duplicated across the client/server boundary. Do not
import the constant from `convex/inbox.ts` either — that module imports `./_generated/server` and
pulling it into the browser bundle is not something this plan is authorised to do.

**3. Criterion 2's numeric half must be asserted in ONE page state.** `126-VALIDATION.md` is explicit:
reading the badge and the Held tab in separate runs cannot catch a contradiction. At unit level that
means a single render whose seeded query results are shared by both readings. The LIVE version of the
same assertion — a spec that reads both from the real deployed data — belongs to plan 126-09, after
the deploy, and neither one alone is the whole property. Say which you established.

**4. Success criterion 1's discipline applies here too: assert on a rendered VALUE.** The acceptance
target is the literal string `9 of 46` in the Held tab given a seeded state, not "the truncation
marker component rendered" and not the absence of a wrong number.
</planner_corrections>
