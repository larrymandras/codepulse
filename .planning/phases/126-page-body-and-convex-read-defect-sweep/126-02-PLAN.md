<objective>
Make the graph snapshot writer produce a chunked, `seq`-keyed blob, and stop producing the ~6,591
entity rows nothing will read once plan 126-05 lands.

Purpose: SWEEP-02. D-05 measured the defect exactly — `getProjectGraph` reads `nodeCount: 4001` plus
`linkCount: 2590` = 6,591 rows in one query against Convex's 4,096-read ceiling, so `/tool-galaxy`
is not slow, it is over the limit. D-06-REVISED settled the remedy after both of D-06's candidate
mechanisms were disqualified by measurement: a single document field lands at 99-101% of the 1 MiB
ceiling, and Convex file storage cannot be read from a `query` at all. This plan builds the WRITE
half; plan 126-05 builds the READ half and cannot be tested until this exists.
Output: a new chunk table, a chunk-producing writer, and the pure split/join helpers the reader will
reuse.
</objective>

<planner_corrections>
**1. The keep-or-retire call D-06-REVISED required the planner to make, made here: RETIRE the WRITES,
KEEP the TABLES.** Grepped across `convex/**/*.ts`, `getProjectGraph` and
`sweepGraphSnapshotVersions` are the only consumers of `graphSnapshotNodes`/`graphSnapshotLinks`.
Once plan 126-05 points the reader at chunks, continuing to write entity rows costs ~6,591 inserts
per ingest with no reader — which is exactly the waste D-06-REVISED's binding text told the planner
to rule on. So `upsertGraphSnapshot` stops inserting them.

It does NOT delete the table definitions, the indexes, or the sweep's handling of them. Two reasons,
both load-bearing:
  (a) Removing a table or index from `schema.ts` makes the deploy print `Deleted table indexes:`,
      which per CLAUDE.md is the ONLY announcement of a schema rollback — and it would destroy the
      legacy rows the sweep still needs to drain.
  (b) The sweep already deletes those rows version by version from `storedVersions`. Left alone, it
      drains the backlog over the next several ingests at its existing bounded rate, which is the
      safe path on a self-hosted instance whose MVCC tombstone GC cannot absorb mass deletes.
`storedNodeCount` / `storedLinkCount` on the meta doc keep their current meaning (how many nodes and
post-dangling-filter links this version holds) and are still written — they are read by
`getProjectGraph`'s return contract, which plan 126-05 must preserve.

**2. The stale-chunk delete goes AFTER the pointer flip, not before it.** `upsertGraphSnapshot`'s own
doc comment (`:44-53`) makes step 7 — the meta patch — deliberately last so that "a crash midway
leaves rows with no list entry" rather than a pointer naming rows that were never written. Deleting
the previous version's chunks BEFORE the flip inverts that guarantee: a partial application would
leave `activeVersion` pointing at a version whose chunks are gone. Insert new chunks, flip the
pointer (carrying `blobChunkCount`), THEN delete chunks for versions older than the new one.

**3. Chunk boundaries must not split a surrogate pair.** `JSON.stringify` does not escape non-ASCII,
so an emoji or other astral character in a node `label` survives into the serialized string as a
UTF-16 surrogate pair. Slicing at an arbitrary index can put the high surrogate at the end of chunk
N and the low surrogate at the start of chunk N+1 — two lone surrogates, which are not
representable in UTF-8 and which a store may reject or silently replace with U+FFFD. The join would
then produce corrupt JSON. Adjust the boundary rather than assuming it never happens; the test for
it is cheap and it has a control that can come out the other way.

**4. `blobChunkCount` exists so the READER can fail loudly.** A reader that just concatenates
whatever rows it finds cannot tell a complete blob from one missing its last chunk — it gets a
`JSON.parse` throw at best and a plausible truncated graph at worst. Recording the count at write
time is what lets plan 126-05 assert completeness. It is `v.optional` only because pre-existing meta
docs do not have it.

**5. No `_generated` regeneration is needed.** `convex/_generated/api.d.ts` imports whole modules as
`typeof import("../graphSnapshots.js")`, so new exports from an existing module flow through without
a codegen step. New TABLES likewise flow through `dataModel.d.ts`'s schema import.
</planner_corrections>
