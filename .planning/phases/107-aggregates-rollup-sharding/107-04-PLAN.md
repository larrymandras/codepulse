<objective>
Capture the pre-deploy half of the D-05 live evidence, immediately before plan 107-05 deploys.

Purpose: this measurement is destroyed by the passage of time and by any container recreate. `docker logs` only retains the current container's stream, and every prior incident of this exact mechanism was cleared by a full recreate. A plan that deploys first has destroyed its own baseline. This plan therefore runs LAST before the deploy and produces a self-describing artifact that plan 107-06 must mirror exactly.

**This plan deliberately does NOT use D-05's literally-stated command.** A live measurement on 2026-08-05 09:34 EDT found two independently fatal defects in that arithmetic:

1. `--since 24h` cannot return 24h of data. The container had been up 49 minutes; the flag silently returns only the uptime window. Running it before and after a deploy compares unequal windows and manufactures an improvement out of nothing. This is a false-green trap.
2. The `1135 retries/24h` figure implies ~47/hour. The live measured rate was ~644/hour on the `aggregates` table alone — roughly 13.6x higher. Any post-fix number compared against 1135 flatters the result.

The corrected method — equal explicit windows, normalized to a per-hour RATE, scoped to the `aggregates` table, paired with traffic volume — is specified in `107-VALIDATION.md` and is what this plan implements.

Output: `.planning/phases/107-aggregates-rollup-sharding/107-OCC-BASELINE.md`. No source file is modified. Nothing is deployed.
</objective>

**Section `## C — Pre-deploy read-total control`**

This is a CONTROL run of the same spot-check plan 107-05 and 107-06 will repeat. Running it BEFORE the change proves the technique itself is sound, so that a post-deploy mismatch is attributable to sharding rather than to the measurement.

Compute, in the shell, from the current clock (all in epoch seconds):
- `H0` = start of the most recent COMPLETE hour = `floor(now/3600)*3600 - 3600`
- `H1` = `H0 + 3600`

Derive the bucket total for exactly the hour `[H0, H1)` using two calls whose difference isolates that one hour. `eventCountsByPeriod` includes every bucket with `bucket_start >= cutoff`, so:
- `A` = sum of values from `eventCountsByPeriod` with `lookbackDays = (now - (H0 - 60)) / 86400`
- `B` = sum of values from `eventCountsByPeriod` with `lookbackDays = (now - (H1 - 60)) / 86400`
- `BUCKET_TOTAL = A - B`

The 60-second offset places each cutoff safely inside its hour rather than on the boundary, so clock skew between this shell and the backend cannot flip which buckets are included. If `BUCKET_TOTAL` comes out negative or wildly implausible, that is window drift, not a result — re-run rather than recording it.

Derive the raw event count for the same hour:
- Run `npx convex run events:listRecent` with `{"limit":5000}` and record the command.
- Count the returned events whose `timestamp` satisfies `H0 <= timestamp < H1`. Record as `RAW_EVENT_COUNT`.
- **Coverage guard, mandatory:** the MINIMUM `timestamp` among the returned events must be strictly less than `H0`. If it is not, the 5000-row window did not reach back past the target hour and the count is a floor, not a count — raise the limit and re-run until the guard passes. Record the observed minimum timestamp and whether the guard passed.

Record `BUCKET_TOTAL`, `RAW_EVENT_COUNT`, and whether they match. Record the two known caveats explicitly rather than leaving them implicit: `listRecent` excludes rows with `archived === true` (nothing should be archived within the last complete hour), and `events.ingest` deduplicates on `idempotencyKey`, so one bucket increment corresponds to exactly one stored row.

If they do NOT match pre-deploy, record the discrepancy and its size but do NOT block the deploy on it — a pre-existing mismatch is a finding about the current system, not about sharding. Say so plainly in the SUMMARY so plan 107-06 compares against the right expectation.

Finish the artifact with a line reading `BASELINE COMPLETE — safe to deploy (plan 107-05)` or `BASELINE BLOCKED — <reason>`.
