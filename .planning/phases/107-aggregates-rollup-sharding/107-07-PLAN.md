<objective>
Gap closure for OCC-01, which `107-06` recorded as `VERDICT: FAIL`.

107-03 sharded the WRITE target but left the READ set as the whole bucket: both
`incrementEventBucket` (`analyticsRollup.ts:43-54`) and `incrementSankeyEdge` (`:101-111`)
`.collect()` every row for the `(metric_type, period, bucket_start)` tuple and match the
dimension key in JS. Convex OCC conflicts on documents **read from or written to**, so any
concurrent ingest patching any row in that bucket forces a retry. Sharding made each bucket
~4.4x wider in rows (23 -> 101 in the measured hour), which is why retries per 1k events
ROSE 1188.5 -> 2025.8 (+70.5%) instead of falling.

> **Correction (2026-08-06, after execution):** the `+70.5%` above should not be read as a
> precise effect size. 107-06's raw counts were later reproduced byte-for-byte and are sound,
> but per-clock-hour OCC counts swing **17x on identical code**, and both sides of that
> comparison were single 2 h samples — so the difference sits inside the noise band
> (`107-OCC-EVIDENCE.md` § H.5). It is quoted here as the motivation this plan was written
> against; the DIAGNOSIS it drove (an unsharded read set) was correct and is what this plan
> fixed. Verdict after this plan: `OCC-01 PASS` (§ I).

This plan narrows the read set to a point lookup. Larry chose the full narrowing (indexed
dimension key AND shard) over the minimal shard-only lever, because shard-only still leaves
same-shard/different-key writes colliding and this phase has already spent one full
measurement cycle on a partial lever.

Expected read set per ingest: 101 rows -> 1.

NOT in scope, and deliberately so: raising `AGGREGATE_SHARD_COUNT`. 107-06's evidence argues
against it while the read set is wide, and once the read set is a point lookup the count is
no longer the binding constraint. Leave it at 8 so this cycle measures ONE variable.
</objective>
