<objective>
Write the Wave-0 write-path contract for aggregate sharding, BEFORE any production code changes.

Purpose: two independent reasons this must land first.
1. **Determinism.** The moment `incrementEventBucket` draws its own shard via `Math.random()`, the existing "increment patch-or-insert" test (`convex/analyticsRollup.test.ts:193-208`) becomes genuinely flaky — the two calls would land on different shards 7 times out of 8 and INSERT instead of PATCH, failing `toHaveLength(1)`. Making shard an explicit parameter and pinning it in the test is a correctness prerequisite, not cleanup.
2. **Regression guard.** Nothing in the suite currently proves that a bucket spanning multiple rows still totals correctly, or that a legacy row with no `shard` field is handled.

These tests are EXPECTED TO BE RED until plan 107-03 lands. That is the established Wave-0 pattern in this very file (see its Phase 88 header comment and the `beforeAll` dynamic-import guard at lines 92-104).

Output: `convex/analyticsRollup.test.ts`, updated in place. No production file is modified by this plan.
</objective>

Write these tests:

1. `"same explicit shard patches the same row"` — two `incrementEventBucket(ctx, "llm_call", 1_700_000_000, 0)` calls. Assert `store.aggregates` has length 1, its `value` is 2, and its `shard` is 0.

2. `"different explicit shards insert separate rows that still sum to the full count"` — `incrementEventBucket(ctx, "llm_call", 1_700_000_000, 0)` then `(..., 3)`. Assert length 2; assert the set of `shard` values is exactly `{0, 3}`; assert each row's `value` is 1; and assert the SUM of `value` across both rows is 2. Assert the sum, not just the count — a count assertion alone is a false-green (107-VALIDATION.md § "Dangerous (False-Green) Assertions" item 4).

3. `"a legacy row with no shard field is not patched by a sharded write (D-04)"` — before calling anything, push a legacy row directly onto `store.aggregates`: `{ _id: "legacy", metric_type: "events", period: "hourly", bucket_start: 1_700_000_000, value: 42, dimensions: { event_type: "llm_call" } }` with NO `shard` key. Assert: the legacy row's `value` is STILL 42; `store.aggregates` has length 2; the new row has `shard === 0` and `value === 1`; and the sum across both rows is 43. This encodes the deliberate choice that the write-path match is a STRICT `r.shard === shard` comparison rather than `(r.shard ?? 0) === shard` — strict equality retires the pre-deploy hot row instead of letting it keep absorbing 1/8 of live writes, and the read side stays correct because every reader sums all matching rows regardless of shard.

5. `"different shards split each sankey edge without changing the edge totals"` — the same call twice with shards 1 and 5. Assert 4 `sankey_edge` rows total; group them by `${source}::${target}` and assert there are exactly 2 distinct edges, each summing to `value` 2.
