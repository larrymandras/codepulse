  <action>
Add to `convex/media.ts` a `pruneTrashBatch` `internalMutation` and its entry point, modelled
structurally on `retention.ts`'s `pruneBatchV3` rather than written fresh.

Declared constants at module scope with explaining comments:
- `TRASH_GRACE_MS` = 30 days in milliseconds (D-08)
- `TRASH_PRUNE_BATCH_SIZE` = 200 — matching `retention.ts`'s `BATCH_SIZE`. Add a comment stating
  why this number and not a larger one: `ctx.db.delete()` counts against Convex's ~4,096-READ
  ceiling, not the 16,000-write ceiling the docs and this repo's older comments point at, and a
  query issued after N deletes in the same mutation additionally merges that transaction's pending
  write set. Cite this repo's Phase 115 evidence.
- `TRASH_PRUNE_MAX_BATCHES` — a per-night ceiling, mirroring `MAX_BATCHES_PER_NIGHT`.
- `TRASH_PRUNE_RESCHEDULE_MS` — the inter-batch delay, mirroring `retention.ts`'s value.

`pruneTrashBatch` args: `{ cursorMs: v.optional(v.number()), batchesDone: v.optional(v.number()) }`.

Handler behaviour:
1. Compute `cutoffMs = Date.now() - TRASH_GRACE_MS`.
2. Read ONE bounded batch via the `by_deletedAt` index, seeked from `cursorMs`, restricted to rows
   whose `deletedAt` is present and less than `cutoffMs`, `.order("asc")`, `.take(TRASH_PRUNE_BATCH_SIZE)`.
   **Never `.collect()`.** If the index cannot express "present and < cutoff" directly, take the
   bounded batch and filter in memory — but the `.take()` bound must come from the index range, not
   from a post-filter over an unbounded read.
3. For each row in the batch, in this order: delete the thumbnail blob first
   (`ctx.storage.delete(row.thumbStorageId)` when that field is populated — the `forge.ts` ordering,
   which is correct and must be kept), then `ctx.db.delete(row._id)`. Guard the blob delete so a
   missing blob does not abort the batch — a row whose blob is already gone must still have its row
   removed, or the janitor wedges forever on one bad row. On the D-01 `local-static-origin` branch
   there is no blob to delete; the host file is reclaimed by the watcher's orphan rule instead
   (see `<interfaces>`) — add a comment saying which branch is live.
4. Carry the last processed `deletedAt` forward as the next cursor. If the batch came back FULL and
   `batchesDone + 1 < TRASH_PRUNE_MAX_BATCHES`, reschedule itself via
   `ctx.scheduler.runAfter(TRASH_PRUNE_RESCHEDULE_MS, internal.media.pruneTrashBatch, { cursorMs, batchesDone })`.
   A short batch means the sweep is done; stop.
5. Return a small result object naming `deletedCount`, `nextCursorMs` and `rescheduled` so the
   behaviour is assertable without reading the database.

Add an adjacent comment stating explicitly what this function must NOT do, so a later editor does
not "simplify" it: no `.collect()`, no unbounded `.take(largeN)`, no query issued after the delete
loop within the same invocation, and no mass delete against the live instance (CLAUDE.md's
operational rules — mass deletes on this self-hosted single-node backend produced the 2026-07-21/22
tombstone incident that took the dashboard down for days).

Also add the comment described in `<interfaces>` naming the host-side orphan rule that plan
`118-08` implements.
