<objective>
Extract the three new prune-chain decisions that Phase 110 introduces — predicate-aware batch bookkeeping (D-02), rotation-start resolution (D-05), and the rotation write decision (D-06) — into `convex/retentionCursor.ts` as pure, dependency-free functions with unit tests, before any of them is wired into the mutation.

Purpose: `pruneBatchV3` is not directly testable — this repo has no `convex-test` harness, which is the stated reason `planNextPruneStep` was extracted in the first place (`convex/retentionCursor.ts:33-35`). The single most dangerous change in this phase is Pitfall 1: once a predicate can skip a doc without deleting it, `lastCreationTime` sourced only from deleted docs leaves the cursor unmoved and re-reads the same 200 rows every batch until the nightly cap burns out — a self-inflicted repeat of the exact head-rescan failure this module exists to fix. That behavior must be provable by a unit test, which means it must live outside the mutation.

Output: three exported pure functions and their tests. No behavior change to the running prune — nothing in this plan is called by `convex/retention.ts` yet.
</objective>

  <action>
Add three exported pure functions to `convex/retentionCursor.ts`. Keep the file dependency-free: no `convex/values`, no `./_generated/*`, no imports at all. `planNextPruneStep` and its interfaces are untouched.

**1. `partitionBatchForPrune`** — the Pitfall-1 fix, expressed as data rather than a loop side effect.

Signature: `partitionBatchForPrune<T extends { _id: unknown; _creationTime: number }>(batch: readonly T[], predicate?: ((doc: T) => boolean) | undefined): { toDelete: T[]; lastCreationTime: number | null }`.

Behavior: iterate the batch in order. A doc goes into `toDelete` when `predicate` is `undefined` OR `predicate(doc)` returns truthy. `lastCreationTime` is set from EVERY doc iterated, deleted or skipped — it ends as the `_creationTime` of the batch's final element, or `null` only when `batch.length === 0`. Do not compute it from `toDelete`.

Docstring must state, in the module's existing voice: that a predicate-skipped doc still advances the cursor; that sourcing `lastCreationTime` from `toDelete` instead would let a full batch of skipped rows leave `planNextPruneStep` with `lastCreationTime: null`, which its `Math.max(lastCreationTime ?? cursorMs, cursorMs)` clamp resolves to an unchanged cursor, re-reading the same `BATCH_SIZE` rows every batch until the nightly cap is exhausted; and that this is the same head-rescan class of failure documented at the top of this file. Cite `D-02`.

**2. `resolveRotationStart`** — D-05's start-index resolution.

Signature: `resolveRotationStart(rawValue: unknown, tableCount: number): number`.

Behavior: return the raw value when it is a finite integer satisfying `0 <= v < tableCount`. Return `0` for every other input — `undefined`, `null`, `NaN`, a non-number, a non-integer, a negative, or `>= tableCount`. Do not throw on any input.

Docstring: a missing or malformed cursor is never worse than the status quo, because `startNightlyPrune` hardcoded `tableIndex: 0` before this phase. The `< tableCount` bound is evaluated fresh every run against whatever `RETENTION_DAYS` currently holds, so it covers both a table being added and a table being removed with no special case. Cite `D-05` and `D-06`.

**3. `planRotationWrite`** — D-06's write decision.

Signature: `planRotationWrite(action: PruneAction, tableIndex: number): number | null`.

Behavior: return `tableIndex` for `"cap-reached"` (tomorrow resumes exactly where tonight stopped). Return `0` for `"done"` (wrap for a fresh full pass). Return `null` for `"continue-table"` and `"next-table"`.

Docstring: `null` means "write nothing". The interior actions must return `null` because writing there would mean one `agentConfigs` write per batch — up to `MAX_BATCHES_PER_NIGHT` writes a night — which is the per-run write growth D-08 explicitly rejects for the module whose whole purpose is reducing writes. Cite `D-05`, `D-06`, `D-08`.
  </action>
