## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, badge internal padding |
| sm | 8px | Compact control spacing (icon cluster gaps) |
| md | 16px | Default element spacing, breadcrumb segment gaps |
| lg | 24px | Page canvas padding (`--pad-page`, unchanged by this phase) |
| xl | 32px | Layout gaps between header zones |
| 2xl | 48px | Header height (D-06, gated — see Header Contract) |
| 3xl | 64px | Not used by this phase's surfaces |

Exceptions (all locked upstream, not introduced by this phase):
- **Command bar max-width 420px** (sketch §7) — not a multiple of 4/8. This is design law from the
  approved sketch, not a new deviation; carry it verbatim.
- **Sidebar width 232px** (SHELL-02, `src/layouts/__tests__/DashboardLayout.test.tsx:194`'s target
  value) — is a clean multiple of 8 (29 × 8), no exception needed, noted only because it changes
  from today's 240px.
- **E-Stop `min-width: 96px`** (sketch §7) — clean multiple of 8. `shrink-0` is already present at
  `EStopButton.tsx:98` and `whitespace-nowrap` at `:101` (no explicit `min-width` utility exists
  today; the planner should verify 96px is actually reached at the narrowest viewport rather than
  assuming these two utilities guarantee it — see Header Contract).
- **Icon-only control hit areas — correction, not an inherited property.** This document originally
  claimed 32×32px was "already the case" for icon buttons in this file, citing `p-1.5`. That citation
  was wrong: the only `p-1.5` button in `DashboardLayout.tsx` (`:338`, the CRT toggle) is not
  icon-only — it carries a visible "CRT" text label, so it isn't a hit-area example either way. The
  two real icon-only controls measure **24×24px**: the hamburger (`:554-560`, `p-1` + `h-4 w-4` icon
  = 4+16+4) and the mobile close-X (`:516-522`, same `p-1` + `h-4 w-4` shape). That clears WCAG 2.2's
  24×24px minimum target size with zero margin — it does **not** meet a 32×32px target. This phase
  **should** move icon-only controls (the hamburger, the close-X, and the new `⋯` trigger) to a
  32×32px hit area, but the planner must treat that as a real check to perform against all three,
  not a property to inherit from existing code.

## Typography

| Role | Size | Weight | Line Height | Font |
|------|------|--------|-------------|------|
| Body | 14px (`text-sm`) | 400 | 1.5 | Geist |
| Label (sidebar nav item) | 13px | 400 | 1.4 | Geist, **sentence case** |
| Eyebrow (domain group header) | 11px | 600 | 1.2 | JetBrains Mono, **uppercase**, `letter-spacing: 0.08em` |
| Heading (breadcrumb active segment) | 14px | 600 | 1.3 | Geist |
| Data (SYS/LAT figures, badge counts) | 12px (`text-xs`) | 600 (`font-semibold`) | 1.2 | JetBrains Mono, `tabular-nums` |
| Display | not used | — | — | — (Phase 125's 40px hero numerals; out of scope here) |

**Weight budget: exactly two weights, 400 and 600.** This is a correction from this document's
first draft, which declared four weights (400/500/600/700) — Phase 124's own invention, since the
sketch findings pin no weight for any role this phase uses
(`references/shell-and-dashboard.md:15-19` names sizes and roles only; the one weight it does pin,
300 for the 40px hero numeral, belongs to Phase 125's out-of-scope Display role). The user ruled:
collapse to 400 + 600.

**Consequence: the nav Label has no weight step over Body (both 400).** An active nav item is
distinguished from an inactive one by the **2px `--primary` left rail + 6% tint background**
(D-14, and the "Active item styling" entry in the Sidebar Contract below) — **not** by weight. Do
not reach for `font-medium` on the active item to recover a distinction the table no longer has;
the rail and tint already carry it.

**This table supersedes two live patterns at `DashboardLayout.tsx`, per pre-validated sketch
design law, not a new call:**
- `NavGroup`'s nav-item label (`DashboardLayout.tsx:109`, currently `text-sm font-mono
  tracking-wider`) → sentence-case Geist, weight 400, per sketch §3 ("Geist sentence case for ALL
  UI labels/nav/buttons — mono removed from chrome") and §8 ("sentence-case 13px items"). This is a
  direct instance of the kill list's "uppercase mono nav labels" entry.
- The domain group header (`DashboardLayout.tsx:91`, currently `text-xs uppercase tracking-widest
  text-primary font-mono font-bold` **plus** a `drop-shadow(...)` text-glow — this citation
  describes the code as it exists today, unmodified by this phase yet) → the eyebrow role above
  (weight 600, i.e. `font-semibold` not `font-bold`), colored `--muted-foreground` (not
  `--primary`), **with the drop-shadow glow removed**. Rationale: design law reserves exactly one
  uppercase style (the eyebrow) and colors it dim, not accent — cyan's usage budget is cut ~80% and
  is "never wallpaper" (design_direction), and a glow on every one of 4 always-visible group headers
  is the same shape as the kill list's "per-nav-item glow" and "nav glow" entries, just applied to
  the header row instead of the item row. This is a natural consequence of SHELL-02 rewriting
  `navGroups` rendering in this phase, not scope creep.

**Exception, explicitly locked, not touched by the table above:** E-Stop's label keeps **mono
type** (`specifics` in `124-CONTEXT.md`: "E-STOP keeps mono type... never wraps"). This is a
deliberate carve-out from "mono removed from chrome" for exactly this one control. E-Stop's own
weight (`font-medium`, `EStopButton.tsx:98`) is pre-existing, unmodified by this phase, and outside
this table's two-weight budget by construction — the budget governs *new* chrome this phase builds,
not an unmodified pre-existing control.

**No new typography tokens are required.** `--ink` / `--ink-dim` / `--ink-data` from the sketch's
source theme file (`sources/themes/default.css`) are **not yet ported** into the live
`src/index.css` — verified by reading the file in full, no `--ink*` custom property exists in any
theme block. This phase does not need them: `--foreground` (heading/active) and `--muted-foreground`
(eyebrow/dim) cover the color roles this phase's chrome touches. `--primary` also already carries the
SYS/LAT figures' color at `DashboardLayout.tsx:575/581` (unchanged by this phase) — that citation is
about **color**, not weight: those spans are currently `font-bold` (700) in the live code, which this
phase's Data role (600/`font-semibold`) supersedes only if/when SYS/LAT relocates into a
Data-role-styled slot per the Header Contract below; until relocated, their existing weight is simply
untouched, not "kept at 700 deliberately". Do not port `--ink-*` speculatively here — if Phase 125's
Pulse ECG hero needs them, that phase names them.

**Accent (`--primary`) reserved for — explicit list, nothing else may use it:**

   var(--primary) 6%, transparent)`), per the sketch's "Active nav rail" CSS pattern verbatim.
2. Sidebar nav-item **hover** state text/icon tint (carried forward from the existing
   `hover:text-primary hover:bg-primary/5` treatment — unchanged).
3. Command bar affordances: the `⌘K` kbd hint and the search icon's hover/focus tint; the focus
   ring on the trigger button.
4. The `⋯` overflow trigger's hover/open state.
5. `BrainHeaderBadge` (pre-existing, unmodified by this phase — it signals the *active* brain,
   which is "live now" by the color law's own definition, so its existing cyan glow is not a
   deviation this phase introduces or must fix).

chip's Nominal state does **not** use `--primary` — it uses `--status-ok`. This is the exact

for "Nominal" would silently recreate that collision inside a brand-new component. See the System
Chip table below.

**Violet (`--astridr`, `#8b5cf6`) is out of scope for this phase** — the color law reserves it for
Ástríðr the entity exclusively, and nothing SHELL-01/02 builds is her voice or her presence. Do not
introduce it into the header or sidebar.

## Header Contract (SHELL-01)

Three zones, matching the sketch's §7 and the locked mapping in `124-CONTEXT.md` D-06 through D-09.

### Zone 1 — Left (breadcrumb, ≥`md`) / Zone 1 mobile (hamburger, <`md`)

- **≥`md`:** breadcrumb per the Copywriting Contract above, inside a `<nav aria-label="Breadcrumb">`
  with the current segment marked `aria-current="page"`.
- **<`md`:** the existing hamburger button (`DashboardLayout.tsx:554-560`) replaces the breadcrumb
  entirely, unchanged in position and behavior (D-09).

### Zone 2 — Center (command bar)

- Unchanged from today's implementation shape (`DashboardLayout.tsx:589-600`): `max-w-sm` container
  → **the sketch's 420px is the target max-width**, `hidden md:flex` (D-09: hides below `md`, ⌘K
  still works, reachable from `⋯`).
- Trigger copy, icon, and `⌘K` kbd hint are unchanged.

### Zone 3 — Right

**Stays visible (six items, D-07):** brain badge → system chip (new) → notification bell → E-STOP
→ `⋯` → user menu.

*Correction to `124-CONTEXT.md`'s own enumeration order*: D-07's prose lists "brain badge, system
chip, notification bell, E-STOP, ⋯, user menu" but today's DOM order at `DashboardLayout.tsx:602-618`
is E-Stop first, then brain badge, then bell. Either DOM order is compatible with D-07's *set* of
six — D-07 fixes *which six stay*, not their left-to-right order within the zone. Recommend keeping
E-Stop first (right-to-left: the most drastic action closest to the edge is a common console
convention, and it avoids reordering more of the existing JSX than necessary) — flagged as the
planner's call, not re-locking an already-decided item.

**Moves into `⋯` (D-07, amended 2026-08-21):** theme switcher, privacy shield, ambient audio, CRT
toggle. **"Help" is deferred, not included.** The original D-07 text and sketch §7
(`references/shell-and-dashboard.md:27`, "⋯ overflow (theme/privacy/audio/CRT/help live there)")
both named a Help entry — but no Help control exists anywhere in the app today (`grep -niE
"help|circlehelp" src/layouts/DashboardLayout.tsx` returns zero matches; control: the same search
for `ThemeSwitcher` returns 4 matches in the same file, so the probe discriminates). Building one is
net-new UI outside a presentation-only regroup, and its shape (a shortcuts sheet, a docs link, a
guided tour) is unscoped. The user ruled to defer it pending its own scoping; `124-CONTEXT.md` D-07
is amended in place to record this. This phase's `⋯` menu therefore holds exactly the four existing
controls named above.

Use `DropdownMenu` (`src/components/ui/dropdown-menu.tsx`) — icon-only trigger (Lucide
`MoreHorizontal` or `Ellipsis`), `aria-label="More options"` (icon-only, no visible text). Each
existing control (`ThemeSwitcher`, `PrivacyShield`, `AmbientAudioPlayer`, `CrtToggle`) is composed
*inside* a `DropdownMenuItem`/`DropdownMenuContent`, not reimplemented — they keep their own
internal state and `localStorage` persistence unchanged; only their mount location moves.

**System chip (new, D-11) — composes `StatusBadge`, does not hand-roll a new component:**

| Chip state | Trigger | `StatusBadge` mapping | Label |
|---|---|---|---|
| Nominal | no critical/error/warning alerts, WS connected | `status="ok"` `tier="quiet"` | "Nominal" |
| Attention | ≥1 warning alert, no critical/error, WS connected | `status="warn"` `tier="quiet"` | "Attention" |
| Critical | ≥1 critical or error alert, WS connected | `status="error"` `tier="strong"` | "Critical" |
| Offline | `useConvexConnectionState().isWebSocketConnected === false` | `status="idle"` `tier="quietest"` | "Offline" |

Data source: `alerts.countBySeverity` (already required by D-10's Alerts badge — one subscription,
two consumers) + `useConvexConnectionState()` (the exact hook already imported at
`DashboardLayout.tsx:3`/used at `:152-153` — this is the "122 D-16 precedent" `124-CONTEXT.md`
cites, now confirmed live rather than assumed). **No new Convex query** — `convex/health.ts`
verified to export only `detectStaleSessions`/`detectStaleAgents` (both `internalMutation`, lines
5/25) and a `healthCheck` `httpAction` (line 48) — zero public queries, confirming D-11's premise.

**Deleted (D-08):** the "Astridr Runtime Telemetry" pill (`DashboardLayout.tsx:563-568`) — pulse
dot + cyan-as-wallpaper, both kill-list shapes, both already banned by POLISH-01. The breadcrumb
occupies its former space.

**Relocated, not deleted (D-08):** SYS/LAT (`:570-585`). This document defers their exact new home
to the plan per `124-CONTEXT.md`'s own Deferred Ideas section (`⋯` menu vs. Dashboard instrument
cluster) — both are compatible with this contract: if placed in `⋯`, render as a `DropdownMenuItem`
pair using the existing `text-xs font-mono` data styling (Typography table's "Data" role — 12px,
`font-semibold`); if deferred to Phase 125's Dashboard work, this phase's `⋯` menu simply doesn't
gain them.

### Header height — MEASUREMENT-GATED, not a fixed number (D-06)

**Do not implement `h-12` (48px) unconditionally.** `DashboardLayout.tsx:551`'s current `min-h-14
flex-wrap gap-y-1` is a control-proven fix (`120-GEOMETRY-EVIDENCE.md`: 981px combined min-content
width vs. 660px available at a 900px viewport, controls silently clipped by the ancestor
`overflow-hidden` at `:517` when the header itself has none). The consolidation this phase performs
(D-07's right zone: 10 controls incl. 2 dividers down to 6; D-08's pill deletion) is *expected* to
remove that overflow, but expectation is not measurement.

**Required sequence, both branches specified:**
1. Build the consolidated 3-zone header exactly as specified above.
2. Re-run the same measurement `120-GEOMETRY-EVIDENCE.md` performed: combined min-content width of
   the three zones vs. available header width, at the narrowest supported viewport (375px per D-09,
   and re-check at 900px since that is where POLISH-06's original defect was found).
3. **If it clears with margin** (i.e., min-content width is comfortably under available width, not
   merely not-currently-overflowing): adopt `h-12` (48px), fixed, no `flex-wrap`, no `min-h-14`.
   This is the target contract from the sketch (§7's "48px" is the design law's stated goal).
4. **If it does not clear with margin:** keep `min-h-14 flex-wrap gap-y-1` (POLISH-06's mechanism),
   and the phase's own closing documentation must say so plainly — do not report 48px as shipped
   when the wrap is what actually shipped. This is not a fallback to be ashamed of; it is the
   difference between a number and a result.

Either branch keeps the header's own `overflow` unset and the ancestor's `overflow-hidden`
unchanged — POLISH-06's finding about *where* the clip happens is independent of which branch wins.

## Sidebar Contract (SHELL-02)

### Structure

- Width: **232px** expanded (was 240px), **48px** collapsed (rail — unchanged, D-14).
- Four collapsible domains, in this fixed order: **Command → Observe → Agents → System**. The
  44-row item-to-domain mapping is locked verbatim in `124-CONTEXT.md`'s `<the_44_row_map>` — this
  document does not restate it; the plan transcribes it directly from CONTEXT per D-01.
- Within-domain item order: preserve the existing deliberate adjacencies called out in
  `navRegistry.ts`'s own comments (Seiðr Suite: Skills/Galdr/Bifröst/Studio stay adjacent; Loom's
  GRAPHS placement carries into its new Observe position) — Claude's Discretion per CONTEXT, not
  re-litigated here.

### Per-domain collapse (new) + whole-sidebar rail collapse (existing) — D-14

- Each domain header is a `CollapsibleTrigger` (`src/components/ui/collapsible.tsx`) wrapping the
  eyebrow label; `CollapsibleContent` wraps that domain's item list. Native `aria-expanded` on the
  trigger, no custom ARIA needed — Radix's `Collapsible` already provides it.
- The **whole-sidebar rail collapse** (`sidebarCollapsed`, `DashboardLayout.tsx:353-359`/`:489`)
  **overrides** per-domain state: at 48px, domain headers render as icon dividers (today's
  `collapsed && <div className="pt-3" />` shape, `:96`) and per-domain open/closed state is held in
  memory but not rendered. Restoring the rail restores whatever domain state was already there —
  nothing is reset by collapsing/expanding the rail.
- Persistence (D-15): `localStorage["codepulse-nav-domains"]`, one JSON object of four booleans
  (`{command: true, observe: true, agents: true, system: true}`), all `true` by default, wrapped in
  the same `try { JSON.parse(...) } catch { <all-true default> }` shape as
  `codepulse-sidebar-collapsed` (`:353-359`) and `codepulse-crt` (`:362-368`) — not a new pattern.

### Active item styling

- Unchanged treatment concept, updated color role: 2px cyan left rail + 6% tint (Accent table
  above), per the sketch's "Active nav rail" CSS pattern. This supersedes the current `is-active
  text-primary bg-primary/10` class (`:111`) only insofar as the *rail* is new geometry (a
  `::before` pseudo-element per the sketch pattern) — the color source (`--primary`) is unchanged.
  Per the Typography section above, this rail + tint is now the *only* signal distinguishing an
  active item from an inactive one — weight is identical (400) on both.
- **`aria-current="page"` must be preserved on the active item.**
  `DashboardLayout.tsx:102` renders each nav item with react-router's `NavLink`, which sets
  `aria-current="page"` on the active link by default; the live code adds no override
  (`grep -c "aria-current" src/layouts/DashboardLayout.tsx` returns **0**, control: 5 `NavLink`
  hits in the same file). SHELL-02 rewrites this exact render path to add the `::before` rail,
  so the requirement is stated explicitly rather than left to the default surviving: an
  implementer swapping to a plain styled `<Link>`, or stubbing the attribute, would silently
  drop the only non-visual signal of which item is active. This mirrors the `aria-current`
  requirement already carried for the breadcrumb.

### Count badges (D-10, D-12)

- **Inbox** and **Alerts** only. No badge on Tasks, Forge, or anything else.
- Render rule (D-12), exact three states:
  1. Query result `undefined` (still loading) → render nothing.
  2. Query resolved, count `> 0` → render the number.
  3. Query resolved, count `=== 0` → render nothing (absence *is* the "nothing waiting" signal —
     do not render a visible `0`).
  4. Query errored → render a dimmed neutral dot with the accessible label from the Copywriting
     Contract (`"Inbox count unavailable"` / `"Alerts count unavailable"`), never a fabricated
     number.
- **Inbox badge styling:** neutral count pill — no severity concept applies to an inbox count.
  Compose the base shadcn `Badge` (`src/components/ui/badge.tsx`, the same primitive `StatusBadge`
  wraps) with `bg-(--surface-3) text-(--foreground) border border-(--hairline)` — a raised neutral
  chip, no color spent, per the quiet-badge law's "color spent only on state" principle (a raw
  inbox count is not a state).
- **Alerts badge styling — recommended, not explicitly locked (flagged below):** derive the same
  worst-severity coloring the System Chip uses, from the same `countBySeverity` result, so the
  sidebar badge and the header chip never disagree about how urgent things are: critical/error
  present → `StatusBadge status="error" tier="strong"` (filled crimson) with the **total**
  unacknowledged count as the label; else warning present → `status="warn" tier="quiet"`; else
  (info-only) → the neutral Inbox-style pill. This is this document's recommendation for
  consistency, not a CONTEXT.md decision — D-10 only says Alerts gets a badge with real backing, it
  does not specify per-severity coloring. The planner may adopt the neutral-only treatment instead
  if simpler; either satisfies D-10 and D-12.
- Data source: `alerts.countBySeverity` (`convex/alerts.ts:109`, unbounded `.collect()` today —
  **must be bounded or index-scoped in this phase**, D-13) and `inbox.listByProfile`
  (`convex/inbox.ts:168`, index-bounded by `profileId` already — not flagged by D-13, left as-is).

### Error boundaries (D-13) — both halves required

- Each shell-level subscription (system chip's alerts read, Inbox badge, Alerts badge) gets its own
  `<SectionErrorBoundary name="...">` — the existing pattern already wrapping `BrainHeaderBadge`
  (`DashboardLayout.tsx:606`), extended to these three new consumers. A `useQuery` throw in any one

## Accessibility Contract

Carried forward from Phases 122/123 — this phase must not reintroduce any of: a sub-AA contrast
pair, a color-only status signal, or an unlabelled icon-only control.

- **System chip:** conveys state via `StatusBadge`'s existing text + tier styling (label text is
  always present — "Nominal"/"Attention"/"Critical"/"Offline" — never color alone). Not an
  `aria-live` region: alerts can change frequently, and a live-announcing shell chip on every route
  would be exactly the kind of noise 123's remediation worked to remove. Static text, read
  normally by assistive tech on demand.
- **Count badges:** the number alone is not the accessible name — pair with `aria-label="{n}
  unread in Inbox"` / `"{n} unacknowledged alerts"` (exact wording is the plan's call; must name
  the domain, not just repeat the visible digit).
- **`⋯` overflow trigger:** icon-only, `aria-label="More options"`. `DropdownMenu` provides
  `aria-expanded`/`aria-haspopup`/keyboard nav (Arrow keys, Home/End, typeahead, Esc) for free —
  verify it, don't reimplement it.
- **Collapsible domain triggers:** `aria-expanded` from `Collapsible` (native), visible label is
  the eyebrow text itself (no separate `aria-label` required since the text is already the
  accessible name).
- **Breadcrumb:** `<nav aria-label="Breadcrumb">`, current segment `aria-current="page"`.
- **Sidebar rail collapse (existing):** already has `aria-label` ("Expand sidebar" / "Collapse
  sidebar", `:274`) — unchanged, verify it still fires correctly once per-domain state exists
  underneath it.
- **Every icon-only header/sidebar control** (hamburger, `⋯`, rail toggle, avatar) already carries
  `aria-label` in the current code — this phase must not add a new icon-only control without one.
- **Icon-only hit areas** — per the Spacing Scale correction above, the hamburger and mobile close-X
  measure 24×24px today, and the new `⋯` trigger should target 32×32px; verify all three rather than
  assuming any of them already clears it.
- **Criterion routes must stay at 0 axe violations** (`123-CLOSEOUT.md`'s 20-cell criterion
  matrix) — this phase's chrome renders on every route, so a regression here is app-wide, not
  page-scoped. The a11y-02 widened-scan backlog (96 objects, 42 routes) is explicitly out of this
  phase's scope per `124-CONTEXT.md`'s Deferred Ideas — do not fold it in, but do not add to it
  either.
