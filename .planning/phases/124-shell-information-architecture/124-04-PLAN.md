### Group string casing — a deliberate change

Today `NavGroupConfig.group` and each item's `group` are UPPERCASE (`"COMMAND"`). Write the new
values in **sentence case**: `"Command"`, `"Observe"`, `"Agents"`, `"System"`.

Reason: plan 124-08's breadcrumb reads the domain name straight out of this registry and renders
`"Observe / Dashboard"` in sentence-case Geist, while the sidebar's eyebrow header renders the same
string uppercased by CSS (`124-UI-SPEC.md` Typography: eyebrow = 11px JetBrains Mono, uppercase,
`letter-spacing: 0.08em`). Storing the display casing and uppercasing in CSS keeps one source of
truth; storing uppercase would force the breadcrumb to title-case it back, which is drift waiting
to happen.

### `CommandPalette` and D-05's rider

`src/components/CommandPalette.tsx:60-72` renders the Pages group as
`<CommandItem key={to} onSelect={...}>` with **no `value` prop**, so cmdk falls back to deriving
the value from rendered text content. `:85-104`'s Links group DOES set an explicit
`value={`${l.title} ${l.url}`}` and its comment names this exact defect class.

`src/components/__tests__/CommandPalette.test.tsx` imports the REAL `navRegistry` (it mocks
`useCommandPaletteSearch`, `useCommandCatalog`, `AstridrWSContext` and `react-router`'s
`useNavigate` — not the registry). Its existing test at `:149-163` reads `data-value` off
`el.closest("[data-value]")` for two same-labelled items and asserts value uniqueness — that is
the exact harness shape to clone. Note it currently proves a Links-vs-Pages collision is safe
(because Links sets an explicit value); it does NOT cover D-05's Pages-vs-Pages case where
neither item has one.
