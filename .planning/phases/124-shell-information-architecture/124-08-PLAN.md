### The chip's four states — locked vocabulary, locked mapping

| Chip state | Trigger | `StatusBadge` call | Label |
|---|---|---|---|
| Nominal | no critical/error/warning alerts, WS connected | `status="ok" tier="quiet"` | `"Nominal"` |
| Attention | ≥1 warning, no critical/error, WS connected | `status="warn" tier="quiet"` | `"Attention"` |
| Critical | ≥1 critical or error, WS connected | `status="error" tier="strong"` | `"Critical"` |
| Offline | `isWebSocketConnected === false` | `status="idle" tier="quietest"` | `"Offline"` |

`Nominal`/`Attention`/`Critical` are fixed by `124-CONTEXT.md`'s Specifics and are not open.
`Offline` is the UI-SPEC's proposal for D-11's unworded disconnected case (Open Question #1);
the defensible alternate it names is `"Reconnecting"`, matching `DashboardLayout.tsx:155`'s
existing `"Convex: reconnecting"` string. **Default: ship "Offline".** If you ship the alternate,
say why in the SUMMARY.

Offline takes precedence over every alert-derived state: when the socket is down the alert counts
are stale by definition, so reporting "Nominal" from them would be a confident claim about data
that is not arriving.

### Data sources — both already present in this file

- `useConvexConnectionState` is ALREADY imported at `DashboardLayout.tsx:3` and used at `:152-153`
  inside `SidebarContent` (`const convexState = useConvexConnectionState(); const isConnected =
  convexState.isWebSocketConnected;`). This is the 122 D-16 precedent D-11 cites, confirmed live.
  The chip needs its own call in its own component scope — the hook is cheap and idempotent, and
  the two existing call scopes are already separate function components.
- `alerts.countBySeverity` — the SAME subscription plan 124-06's Alerts badge already issues
  ("one subscription, two consumers", D-10). Convex dedupes identical queries client-side.
  Read it directly with `useQuery`, or through the D-12-corrected `useAlertCounts()` from plan
  124-02 — **either is fine, but it must be a source that preserves `undefined`**. Never a source
  that fabricates a zeroed shape: a chip reading "Nominal" because the query has not resolved is
  precisely the defect POLISH-04 exists to prevent.

### Colour law — the one trap here

`--primary` is NOT used by the chip in any state. The UI-SPEC's Color section is explicit:
"the system chip's Nominal state does **not** use `--primary` — it uses `--status-ok`. This is the
exact distinction TOKEN-02 (Phase 122) existed to enforce (healthy ≠ interactive)." Giving the chip
cyan for Nominal would silently recreate that collision inside a brand-new component. `StatusBadge`
already resolves the correct token per semantic + tier — pass the semantics from the table above
and do not override its colours.

### `StatusBadge` call convention

`src/components/StatusBadge.tsx:163-176` — props `{ status, label, tier? }`. `status` is typed
`"ok" | "error" | "warn" | "idle" | string`; any value not in `legacyMap` falls through
`defaultTierForSemantic` (`:94-98`). Pass semantic + explicit `tier` + explicit `label` together,
which is the "direct-semantic-literal caller" convention the component's own comments at `:88-93`
describe. Do NOT build a new `<SystemChip>` component from scratch.

### Accessibility

The chip's state is carried by its LABEL TEXT, always present, never by colour alone. It is NOT an
`aria-live` region — alerts change frequently and a live-announcing chip on every route is exactly
the noise Phase 123's remediation removed. Static text, read on demand.
