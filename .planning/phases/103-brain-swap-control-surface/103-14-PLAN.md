<objective>
Close the OBS 7 gap found by the 103-13-T1 live checkpoint (2026-07-29).

`GlobalSwapModal.runRevert` hardcodes `dispatch({ type: "swap.set", target: "brain", restore: true })`.
Ástríðr defines `restore=true` as "clears the override (`value` ignored)"
(`astridr/api/ws_commands.py:233`, handler at `:1100-1105`), so "Revert global swap" is really
"clear global override". That is correct only when nothing was in force before the swap. When a
global override WAS in force — the exact scenario 103-13-T1 observation 2 sets up — reverting
silently discards it instead of restoring it.

Observed live: badge `claude-haiku-4-5-20251001 (global)` → swap to `claude-opus-4-8` → "Revert
global swap" → badge `unknown`, not back to Haiku 4.5.

This is a CLIENT-side gap, not an Ástríðr protocol limitation: `{"target": <value>}` with
`restore: false` already sets the override to any value, and the component already has
`modelOverride` in scope (`GlobalSwapModal.tsx:123`, via `useGlobalBrainOverride()`).
</objective>

<task type="auto">
  <name>Task 1: Capture the prior global override and revert to it (103-14-T1)</name>
  <files>src/components/brains/GlobalSwapModal.tsx, src/components/brains/GlobalSwapModal.test.tsx</files>
  <action>
In `runSwap`, BEFORE the `dispatch` call, capture the current `modelOverride` into a ref
(e.g. `priorOverrideRef.current = modelOverride`). It must be captured at dispatch time, not read
live inside `runRevert` — by the time a revert fires, `modelOverride` already holds the NEW engine,
so reading it late would revert to the engine being reverted FROM.

In `runRevert`, branch on that captured value:
  - prior override was a non-empty string → `dispatch({ type: "swap.set", target: "brain",
    value: prior, restore: false })` and `setConfirmTarget(prior)`
  - prior override was null/absent → keep today's `dispatch({ ..., restore: true })` and
    `setConfirmTarget(null)`

Do NOT change the D-14 readback effect — it already compares `modelOverride === confirmTarget`
and works for both branches once `confirmTarget` is set correctly. Do not weaken it into
confirming from the ack.

Reset `priorOverrideRef` in the same new-target effect that resets snapshot/outcome
(`:157-166`), so a genuinely new target does not inherit a stale prior value.

Add tests covering: (a) revert after a swap that had a prior override dispatches
`value: <prior>, restore: false`; (b) revert after a swap with NO prior override still dispatches
`restore: true`; (c) the captured value is the pre-swap one even when `modelOverride` has since
changed to the new engine; (d) the outcome stays `confirming` until the readback matches the
restored value, and does not resolve from the ack.
  </action>

  </verify>
