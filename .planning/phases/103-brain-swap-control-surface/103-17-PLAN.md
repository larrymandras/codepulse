## The subtlety that makes the obvious fix WRONG — read this before writing code

`BrainPicker.tsx:376-387` builds `globalSwapProfiles` from `useActiveEngine()` (the
`activeEngineSnapshots` telemetry map), which has zero rows for the real profiles, so every
profile renders `mode: "inherited"` and `currentModelDisplayName: "Auto"`.

Do **NOT** "fix" this by having the current-engine column fall back to
`modelPreferences.primary`. `src/hooks/useActiveEngine.ts:11-19` refuses that fallback ON PURPOSE
and says why: that field "holds a persisted CONFIG value, not a live reading, and presenting it as
live state is exactly the v9.0 VitalsRail active-profile trap BSC-01 exists to remove." Making the
`current` column read config would violate D-14 and re-open the very defect this phase exists to
close. "Auto" for an unreported profile is HONEST and must stay.

The actual defect is narrower: **`mode` / the pinned-default count is a CONFIG question, not a
telemetry question.** "Does this profile have a pinned default that a global override will shadow?"
is answered by `profileConfigs.modelPreferences.primary`, which `BrainPicker` already has in hand
at `:219` via `useProfileConfigs()` — it simply never reads it. Splitting those two concerns is the
fix: keep the live column live, and derive the pin from config.

options; pick one and justify it:
  (a) keep `mode` as the telemetry-reported value and add a SEPARATE `hasConfiguredDefault`

      type.

change the meaning of an existing field without recording it.

In `GlobalSwapModal`, drive `pinnedCount` (`:182`) and the shadowing warning (`:273-282`) off the
configured-pin signal. Do not change the D-14 outcome/readback machinery.
