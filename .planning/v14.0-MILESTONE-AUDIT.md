### ⚠️ INT-01 — spec asserts the presence of the panel Phase 111 deleted (medium)

`e2e/command-center-breakpoints.spec.ts:37` lists `'ACTIVE AGENTS'` in `PANEL_HEADERS`, and
`:165-168` asserts every entry is **visible**. Commit `87dafe30 feat(111-02)` deleted
`ActiveAgentsPanel`. **Two tests in this repo now assert contradictory things** —
`src/pages/Chat.test.tsx:1005,1012` assert `queryByText("ACTIVE AGENTS")).not.toBeInTheDocument()`.

*Control (scope):* 6 of the 7 `PANEL_HEADERS` labels resolve to a live non-test component in
`src/components/control-center/`; `ACTIVE AGENTS` resolves to 0. The defect is exactly one entry —
the class does not extend further.

**Why it went unnoticed:** the spec `test.skip`s when the Clerk gate is present (`:104-109`), and
`:155-159` records that "the Clerk gate skipped every tier." So against the default `:5173` server it
*skips*; it fails only when run properly unskipped against `dev:noauth` on `:5181`, which is where
both `119-VERIFICATION.md` gap 6 and `113-HANDOFF.md` observed it failing 3/3. It is also Playwright,
so `npx vitest run` cannot surface it.

**Affects MISSION-03's completeness claim** ("no affordance asserting an unbacked state *anywhere*")
at the e2e layer. Both prior docs flagged it as "belongs to the in-flight Phase 111"; Phase 111 has

*Not a defect, called out so it isn't mistakenly "fixed":* `src/components/AgentTopology.tsx:196`

### ⚠️ INT-02 — `pipelineRuns` has no retention disposition (medium)

`convex/loom.ts:211` inserts a row into `pipelineRuns` from the bearer-gated emit route
(`loomHttp.ts:55` → `api.loom.recordStepEvent`), one per run, machine-fed. The per-row `stepEvents`
array **is** bounded (`LOOM_STEP_EVENT_CAP = 200`, `loom.ts:25,51-52`) and `schema.ts:2231-2234`
documents that cap — but the **row count** has no stated disposition. `pipelineRuns` is absent from
`RETENTION_DAYS` (deployed `listRetentionPolicy` readback = 19 keys, none of them `pipelineRuns`) and
is not named in `retention.ts`'s exemption block, which explicitly names `prompts`, `promptVersions`
and `links`.

*Control:* `convex/loom.ts` contains no `ctx.db.delete` at all, against `convex/galdr.ts:280` which
does — so the absence of a row-level prune is real, not a search artifact.

**No alert can ever fire for it:** `retention-health-check.ps1:61` enumerates tables from the live
policy, so a table outside `RETENTION_DAYS` is structurally invisible to the check.

Growth is agent/operator-driven, not a firehose, so this is not an imminent hazard — 4 runs exist
today. It is a **consistency gap against DUR-01's own stated rationale**: every other new table in
this lineage was bounded pre-emptively for exactly this reason (`gatewayQuotaSnapshots` D-20,
`toolPolicyEvents` D-05, `activeEngineSnapshots` D-10, `controlVerbSwaps` D-14), with `retention.ts`
framing the pattern as "bounded BEFORE it can ever need a mass delete." Either bound it or record the
exemption where the other three are recorded.

### ⚠️ INT-03 — Loom's bearer gate is bypassable at the mutation layer (medium)

`convex/loom.ts:140` `upsertPipeline` and `:232` `recordStepEvent` are declared `mutation({`, not
`internalMutation({`. Public mutations live in the client-callable `api.` namespace, so any holder of
the shipped `VITE_CONVEX_URL` can invoke them directly and bypass `validateLoomAuth`
(`loomHttp.ts:38`) entirely.

*Control:* this is the exact write path Phase 108 closed by rule — `convex/activeEngine.ts:79`
`recordRouting = internalMutation` and `convex/controlVerbSwaps.ts:46` `record = internalMutation`,
both with rationale comments naming the forgeable-write-path risk.

Cost to fix is near zero: the UI never calls either mutation, and the documented CLI consumer
(`npx convex run loom:upsertPipeline`) works against internal functions.

*Fairness caveat:* unauthenticated public mutations are repo convention, not something Phase 119
introduced — `galdr.ts` and `bifrost.ts` have no `ctx.auth` either. This is a deviation from Phase
108's telemetry-write rule specifically, not from repo norms.

### ⚠️ INT-04 — the live Galdr library is 95% e2e test pollution (medium)

**Verified by direct query against the self-hosted backend, 2026-08-11:** `galdr:list` returns
**19 prompts, 18 of them named `E2E send probe <timestamp>`.** The single real prompt is
`Adversarial plan review`. `galdr:list` filters archived rows (`galdr.ts:75-76`), so all 18 are
unarchived and rendering on `/galdr` right now.

- `e2e/galdr.spec.ts:41` creates a real prompt against the live self-hosted instance.
- Cleanup is inline at the end of the test body (`:88-105`), **not** a fixture teardown — `grep -n
  "afterEach\|afterAll" e2e/*.spec.ts` returns zero hits across all 13 specs. Any failure at steps
  2–4 leaks the row permanently, and the spec's own comment at `:26-27` records that it *has* failed
  intermittently under load.
- `prompts` is retention-exempt by design (`retention.ts:105-120`), so nothing ever removes them.

Confined to one spec: `e2e/loom.spec.ts` and `e2e/bifrost.spec.ts` contain no mutation calls.

This is the one finding with a visible cost to Larry today — the page he actually uses is mostly
garbage rows. The fix has two halves: purge the 18 leaked rows (via the existing per-row archive
path, never a bulk delete on this instance), and move cleanup into a real teardown.
