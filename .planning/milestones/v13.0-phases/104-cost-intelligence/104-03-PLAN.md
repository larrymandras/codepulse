<objective>
Widen the hourly rollup so it stores tokens by model rather than only pre-aggregated dollars
(D-04), and backfill the existing retention window so a rate correction re-prices history rather
than only the future.

Purpose: D-01/D-03 need the read path to do the multiply. That is only possible if the rollup
carries input and output token counts per dimension key — the existing `"tokens"` metric_type
collapses both into a single `totalTokens` number, which cannot be re-priced once input and output
rates differ.
Output: two new `metric_type` values in the existing `aggregates` table, plus a resumable backfill.

No schema change is required: `aggregates.metric_type` is already `v.string()` and `rollupDaily`
groups generically by `metric_type` + `dimensions`, so daily buckets follow automatically.
</objective>

Without a backfill, D-04's "history re-prices back to the start of retention" is false for every
hour before this deploy: those hours have `cost` and `tokens` buckets but no prompt/completion
split, so the read path can only price them from this deploy forward.

Add `export const backfillTokenSplit = internalMutation({ args: { maxHours: v.optional(v.float64()) } })`
to `convex/aggregates.ts`.

Rules, all mandatory:
- Work BACKWARD from the most recent complete hour toward the retention floor, one hour bucket at
  a time, capped at `args.maxHours ?? 6` hours per invocation. It is INSERT-ONLY: it never patches
  and never deletes an existing `aggregates` row. Per CLAUDE.md, no bulk patch or delete may run
  against the live self-hosted instance.
- Resume position is stored in `agentConfigs` under `configKey`
  `"phase104.tokenSplitBackfill.cursor"` (value = the `bucket_start` epoch-second of the next hour
  to process). Read it with the existing `by_key` index. When absent, start from
  `Math.floor(Date.now() / 1000 / 3600) * 3600 - 3600`.
- For each hour: read `llmMetrics` with the SAME paginated 500-row shape as `computeHourly`
  (`by_timestamp`, `gte hourStart`, `lt hourEnd`, `filter archived != true`, cursor pages) — never
  a bare `.collect()`. Accumulate `promptByDim` / `completionByDim` on the identical 4-segment key,
  then insert `tokens_prompt` / `tokens_completion` rows behind the same per-metric-type
  idempotency guards Task 1 introduced. Factor the accumulate+guard+insert logic out of
  `computeHourly` into a shared non-exported helper so the two paths cannot drift.
- Stop early and write a terminal sentinel into the cursor (the string `"done"`) when the next
  hour would fall before the retention floor, computed from the retention window
  `convex/retention.ts` already defines — do not hardcode a second, independent retention number.
- Return `{ hoursProcessed, rowsInserted, nextCursor, done }` so the operator can see progress and
  decide whether to invoke it again.
- Do NOT register a cron for it. It is run manually via
  `npx convex run aggregates:backfillTokenSplit '{"maxHours": 6}'`, repeatedly, until `done` is
  true. Document that invocation in the function's doc comment. A cron would reintroduce exactly
  the self-retriggering long-running mutation that killed `evaluateInternal` on 2026-07-14.

Extend `convex/aggregates.test.ts` with a `describe("backfill")` block asserting:
- an invocation with `maxHours: 2` processes exactly two hour buckets and no more;
- the returned `nextCursor` is the third hour back;
- an hour whose `tokens_prompt` rows already exist inserts no duplicate for that metric type;
- reaching the retention floor returns `done: true` and writes the terminal cursor sentinel;
- the mutation issues no `db.patch` and no `db.delete` call on the fake ctx.
  </action>
