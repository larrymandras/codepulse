# Phase 103 — UI Design Contract

> Visual and interaction contract for the Brain-Swap Control Surface. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Reads together with `103-CONTEXT.md` (locked decisions D-01..D-17) and the astridr design spec `2026-07-17-astridr-brain-swap-design.md` — this file resolves the visual/interaction gray areas both left to `/gsd-ui-phase 103`.

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn (already initialized — `components.json` detected, no gate needed) |
| Preset | official shadcn registry only; `registries: {}` in `components.json` — no third-party sources |
| Style | new-york, baseColor neutral, cssVariables true, radius 0.5rem |
| Component library | Radix (via 30 shadcn primitives in `src/components/ui/`) |
| Icon library | Lucide (`lucide-react`) only |
| Font | Geist (body + headings), JetBrains Mono (code, mono/tabular data — quota %, health status, "switching to X…") |
| Theming | Token-driven, `<html data-theme>`; every color below is a CSS var, never a literal hex, so the contract holds unchanged across `cyan` (default) / `emerald` / `readable` (WCAG-AA, glow suppressed) / `aubergine` / light "Paperclip". `--glow-*` tokens already resolve to `0 0 0 transparent` under `readable` (`src/index.css:270-273`) — use `shadow-[var(--glow-xs)]` etc. freely, no theme-specific branching needed in this phase's components. |

**One documented exception to "never hardcode hex":** `PROVIDER_COLORS` (`src/lib/providers.ts:38`) stores literal per-provider brand-identity hexes (already used dashboard-wide for provider dots/charts). This phase's picker rows and badges reuse that existing const for the provider-family color dot — this is provider *identity*, not a theme surface color, and pre-dates this phase. Do not invent a second identity-color source.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps inside chips/dots |
| sm | 8px | Compact row internals (dot · name · chip · dot · bar) |
| md | 16px | Default element spacing — picker row padding, modal section gaps |
| lg | 24px | Section padding — modal body padding, Settings row groups |
| xl | 32px | Layout gaps — between picker groups (Subscription/API/Local) |
| 2xl | 48px | Not used in this phase's surfaces |
| 3xl | 64px | Not used in this phase's surfaces |

Exceptions:
- **Composer pill / header badge height = 32px (`h-8`)**, not the 40px standalone-icon-button precedent already in `ChatInput.tsx` (mic/send buttons) — the pill carries a text label, not just an icon, so a slightly shorter height keeps the composer row's vertical rhythm tight. Horizontal padding is `px-2` (8px, the declared `sm` token) each side, giving a comfortably-clickable width for a typical engine name plus dot and chevron at mouse precision. This falls below the 44px mobile touch-target guideline by design — this is a desktop-first, mouse-driven dashboard control, not a touch surface, matching every other icon-height control already in this header cluster (`EStopButton`, `NotificationBell`, `ThemeSwitcher` all sit at similar heights).
- **Health dot = 6px**, quota bar height = 4px (`h-1`) — matches the existing `GatewayQuotaPanel`/`ProviderHealthPanel` bar geometry (`h-1 rounded-full`), reused verbatim for visual consistency with the provider-health surfaces this phase composes against.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 (regular) | 1.5 |
| Label | 12px | 600 (semibold) | 1.4 |
| Heading | 16px | 600 (semibold) | 1.3 |
| Display | 18px | 600 (semibold) | 1.3 |

Only two weights declared (400, 600) — this phase's new components do not use `font-medium`/500 even though it appears in older code (`Settings.tsx` profile rows); normalize new markup to regular-or-semibold only.

- **Body** — row labels, engine names, modal body copy, fallback-notice text.
- **Label** — uppercase mono chips/badges (`STUB`, `API`, `SUB`, quota `%`, health status word), "switching to X…" pending text. Use `font-mono tabular-nums` for any numeric value (quota %, TTL countdown). All Label-role text uses `text-xs` (12px) — no smaller size exists in this scale; do not introduce `text-[10px]` anywhere in this phase's components.
- **Heading** — picker group headings ("Subscription" / "API" / "Local"), Settings section headers (matches existing `text-base font-semibold` convention at `Settings.tsx:635`).
- **Display** — confirm-modal titles only ("Swap all profiles to Sonnet 5?").

## Color

The generic 60/30/10 split governs page-level surface composition; this phase is component-level, so it's expressed here as three semantic channels layered on top of the existing surface tokens.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--background)` / `var(--card)` | Picker popover background, modal background, Settings row background |
| Secondary (30%) | `var(--muted)` / `var(--card)` at reduced opacity | Picker row group backgrounds, quota-bar track, inactive scope-selector segment |
| Accent (10%) | `var(--primary)` | Reserved for: (1) the primary CTA button in the picker/modal ("Switch to {engine}", "Confirm swap"), (2) the currently-selected row highlight in the picker, (3) focus rings, (4) the header badge's "live/confirmed" pulse dot when the shown engine is server-confirmed (not pending, not stub) |
| Destructive | `var(--destructive)` | Reserved for: hard swap failure text/icon in the partial-failure result list; nothing else in this phase (no destructive *action* — swaps are revertible, D-10) |

Additional semantic channel (not part of the 60/30/10 split, used throughout every surface):

| Token | Usage |
|-------|-------|
| `var(--status-ok)` | Health dot = reachable/authenticated; quota bar fill ≥20% remaining; partial-failure result "switched" rows |
| `var(--status-warn)` | Health dot = degraded/near-quota; quota bar fill <20%; expensive/unknown-model inline confirm border+text; stub-data banner/tag; CLI→API fallback toast |
| `var(--status-error)` | Health dot = unreachable/unauthenticated; quota bar fill <5%; partial-failure result "failed" rows |
| `var(--status-info)` | Pending overlay ("switching to X…") on the pill, header badge, and Settings row — **never `--primary`**, matching the established v11.0 Phase-100 SkillRow pending-overlay rule that pending/unconfirmed state must never visually read as active/selected |

Accent reserved for: primary CTA buttons, the picker's selected-row highlight, focus rings, and the header badge's confirmed-live pulse dot. Never used for pending, stub, or health/quota indication — those are semantic-status tokens, not accent.

## Surface-by-Surface Contract

### 1. Chat composer pill (`src/components/ChatInput.tsx`)
- New row **above** the existing textarea/mic/send flex row (mirrors the skill-chip-row precedent in `Chat.tsx`) — do not crowd the existing 40px mic/send row.
- Pill: `h-8` button, `rounded-full`, `border border-(--border)` idle / `border-(--primary)` on hover-open. Content: `[6px provider-color dot] [EngineDisplayName, Body 14px] [ChevronDown 12px]`.
- Session-override vs pinned-default distinction (D-02): the pill's primary label is always whichever is **actually in force**. If a session override is active, append a small `Clock` icon + "1h" countdown in Label typography, `--status-info` tint (informational, not alarming). If only a pinned default is active, append a small `Pin` icon, `--muted-foreground` tint. Never show both as if both were "current" — only one is in force at a time.
- Pending (D-15): pill keeps its truthful current label; a `--status-info` pulsing dot replaces the chevron and " · switching to {X}…" (Label typography) appends after the name. On failure the pending suffix simply disappears — no error styling on the pill itself, the failure lives in the toast (D-15's "nothing to roll back" rule).
- Stub tag: small dashed-border `STUB` chip (`border-dashed border-muted-foreground/40 text-muted-foreground`, Label typography) appended after the pending state slot, only rendered when the stub adapter is active.
- Opens the rich picker (`Popover` anchored to the pill, `cmdk` `Command` inside).

### 2. Header active-brain badge (`DashboardLayout.tsx` status cluster, ~line 577)
- Inserted into the existing `flex items-center gap-1.5 sm:gap-2 bg-primary/5 ... rounded-md border border-primary/10` cluster, between `EStopButton` and the `NotificationBell` divider (leftmost — brain identity is as fundamental as the e-stop, ahead of notification/theme/audio controls).
- Same visual language as the composer pill but icon-only by default on narrow viewports (`hidden sm:inline` for the text label, matching the cluster's existing responsive pattern), full `[dot] EngineName` on `sm:` and up.
- **Accessible fallback for the collapsed state:** the badge button always carries `aria-label="Active brain: {EngineDisplayName}"` (or `"Active brain: Mixed brains"` in the mixed state) regardless of viewport, so the active engine is announced to assistive tech even when the text label is visually hidden below `sm:`. Also wrap it in a `Tooltip` (already installed, `tooltip.tsx`) surfacing the same text on hover/focus — the cluster already sits inside a `TooltipProvider` (`DashboardLayout.tsx:576`), so this reuses the existing pattern every other icon-only control in the cluster follows, rather than introducing a new one.
- **Mixed-engine handling (resolved gray area):** the header badge is dashboard-wide, not bound to one profile. When the badge has no single-profile scope AND ≥2 distinct engines are active across profiles, render "Mixed brains" (Body 14px) with a 3-dot stacked cluster (each dot = one distinct engine's `PROVIDER_COLORS` value, `-ml-1` overlap) instead of a single dot. When all profiles agree, show that engine plainly like the composer pill. **Never silently pick one profile's value and present it as "the" engine** — that would recreate the BSC-01 VitalsRail trap this phase exists to kill. Click always opens the picker; when opened from the mixed-state badge, the picker's scope selector defaults to "All profiles" (still resets to "This profile" on next open per D-08 — this is a one-time contextual default from *this* entry point only, not a persisted preference) and shows the per-profile breakdown list (same row shape as the global-swap confirm modal, without the confirm action) above the swap controls.
- Confirmed-live pulse dot (`--primary`, small, `animate-pulse`) only renders when the shown value is genuinely server-confirmed (D-14, Convex-reactive) and not pending/stub.

### 3. Rich brain picker (grouped Subscription / API / Local, D-07)
- **Focal point:** the search input (`CommandInput`) is the picker's focal point — it auto-focuses on open and sits directly below the scope selector, drawing the eye first via cursor placement. Row content (dot/name/chips) is deliberately kept to Body/Label sizes so no row visually competes with the search focus.
- `Popover` + `Command` (cmdk) — reuse the `command.tsx` primitive already installed, matching `CommandPalette.tsx`'s `CommandGroup`/`CommandInput` composition.
- Top of picker, **inside** the popover, above the search input: scope selector using the already-installed `toggle-group.tsx` primitive, 2 segments — "This profile" / "All profiles". Selected segment = `--primary` background; unselected = `--muted`. **Resets to "This profile" every time the picker opens** (D-08), except the one contextual exception noted above (opened from a mixed-state header badge).
- `CommandInput` — standard fuzzy search placeholder: "Search brains…".
- Three `CommandGroup`s, in this fixed order: **Subscription** (CLI gateway providers: `claude-cli`, `codex`, `antigravity`, `claude-sdk` — `GATEWAY_PROVIDERS`), **API** (keyed model ids under `anthropic_direct`/`openrouter` — Opus 4.8 / Sonnet 5 / Fable 5 / Haiku 4.5 and any other open-registry id), **Local** (`ollama`). *(This grouping is inferred from the existing `PROVIDER_BILLING`/`GATEWAY_PROVIDERS` split in `src/lib/providers.ts` — the real open-registry catalog shape is a `103-CONTRACT.md` deliverable, not yet fixed; planner should confirm this mapping against the final catalog payload.)*
- Each row (D-07 shape), left to right: `[8px provider-color dot]` `[EngineDisplayName, Body 14px, flex-1]` `[billing chip]` `[6px health dot]` `[quota bar or "∞"]`.
  - Billing chip: `Badge variant="outline"` sized down (`text-xs uppercase px-1 py-0`, Label typography — 12px, the smallest declared size; do not drop to `text-[10px]`), text "API" or "SUB" — neutral border color (`--border`), never accent or status color (billing is identity metadata, not a state signal).
  - Health dot: `--status-ok`/`--status-warn`/`--status-error`, sourced from `useProviderHealth()` — reuse the hook, but render with **tokenized** colors (this phase's new rows do not carry forward `ProviderHealthPanel`'s hardcoded `bg-green-500`/`bg-red-500`/`bg-yellow-500` — those predate the token system; new code uses `bg-(--status-*)`). Color is never the sole differentiator: each dot is wrapped in a `Tooltip` (already installed, `tooltip.tsx`) revealing the Label-typography health status word ("reachable" / "degraded" / "unreachable") on hover/focus — this is the concrete surface for the "health status word" the Typography table's Label role already lists.
  - Quota bar: shadcn `Progress` primitive (`progress.tsx`, already installed — compose it, don't hand-roll the div-based bar `GatewayQuotaPanel` uses), `h-1 w-10`, indicator color `--status-ok`/`--status-warn`/`--status-error` by remaining-% thresholds (≥20% ok, 5–20% warn, <5% error — matching the existing threshold logic in `ProviderHealthPanel.tsx:45-51`, just re-themed). Subscription-billed rows show a static full-width `--status-ok` bar or the mono label "∞" instead (no real quota concept).
- Row click on a **normal-tier** model: dispatches the swap immediately via `useCommandDispatch`.
- Row click on an **expensive or unknown-tier** model (resolved gray area — inline, not a modal): the row **does not fire immediately**. It expands in place (row height grows, border becomes `--status-warn`) to show the confirm copy (see Copywriting Contract) + `[Cancel]` (ghost, closes the expansion) `[Confirm swap]` (small `--status-warn`-bordered primary button). Rationale: full modal friction (D-09) is reserved for the genuinely higher-blast-radius global swap; a single-profile swap onto a pricier model is lower-stakes and shouldn't interrupt the picker flow. If scope is simultaneously "All profiles" **and** the target is expensive/unknown, the two frictions do not stack — the row still dispatches into the global-swap modal (below), which gains one extra `--status-warn` warning line for the cost tier instead of a second confirmation surface.
- Stub banner: when the stub adapter is active, a persistent (non-dismissible) strip at the very top of the popover, above the scope selector — `bg-(--status-warn)/10 text-(--status-warn) text-sm px-3 py-2 flex items-center gap-2` with a `FlaskConical` icon (Lucide) and the banner copy from the Copywriting Contract.

### 4. Global-swap confirmation modal (D-09/D-11)
- `Dialog` primitive (`dialog.tsx`). Title = Display typography (18px/600).
- Body: a list, one row per affected profile — `[ProfileName]` `[CurrentEngineDisplayName]` `→` `[NewEngineDisplayName]`. A small `Pin` icon precedes `CurrentEngineDisplayName` when that profile's current value is a pinned default (flags it will be overwritten) — no icon when it was only an inherited/session value.
- Warning line(s), `--status-warn` text with a small `AlertTriangle` icon, appear **above** the row list when applicable: the pinned-defaults count (D-11) and/or the expensive/unknown-model addendum (resolved gray area, above).
- Footer: `[Cancel]` (ghost/outline) `[Swap all profiles to {EngineDisplayName}]` (primary, `--primary` background) — **no type-to-confirm input**; the informational row list *is* the friction (D-09 explicit).
- **This same Dialog shell transitions into the result state** after dispatch rather than closing and relying on a toast alone: rows flip from `current → new` to a resolved state per row — switched rows get a `Check` icon in `--status-ok`; failed rows get an `X` icon in `--status-error` plus the failure reason inline, and **keep displaying their real, unchanged engine** (D-12 — never show the attempted target as if it landed). The dialog's footer becomes a single `[Done]` button. This avoids a modal that closes with no detail and a toast that can't hold N rows of partial-failure detail.
- On dismiss (either Cancel pre-dispatch, or Done post-result): a `sonner` summary toast fires — "{N} of {M} profiles switched to {EngineDisplayName}." with a `Revert` action button (D-10) that persists until superseded by the next swap (global or per-profile), per the existing `useCommandDispatch` toast convention.

### 5. Revert-global-swap affordance (D-10)
- Lives on the summary toast's action slot (sonner supports action buttons) — no separate persistent UI chrome. "Revert" fires a new `gateway.model.set` batch restoring each profile's prior engine **and pin status** (D-11) from the client-held snapshot taken before the original swap.
- A revert itself produces a fresh (smaller) result — reuse the same Dialog result-state row list if the revert also partially fails; otherwise a plain success toast.

### 6. Partial-failure result surface (D-12)
- Covered by the Global-Swap modal's result-state transition above for the *global* case.
- For a **per-profile** swap failure (not global), no modal — just the existing `useCommandDispatch` error toast pattern (`toast.error(result.error)`), and the composer pill / header badge / Settings row simply drop their pending suffix and keep showing the real unchanged engine (D-15).

### 7. Pending / in-flight treatment (D-15)
- One shared visual vocabulary across all three homes (composer pill, header badge, Settings row): `--status-info` pulsing indicator + " · switching to {X}…" Label-typography suffix, layered over the still-truthful current-engine label. Never optimistic — the base label never changes until Convex-reactive telemetry (D-14) confirms it.

### 8. Session-override vs pinned-default distinction (D-02)
- See composer pill spec above (§1) — the same `Clock`-icon-1h-countdown vs `Pin`-icon secondary-line pattern applies identically in the header badge and the Settings → Agents row. This is the single visual rule this phase relies on to keep D-02 unambiguous everywhere the engine is displayed.

### 9. Settings → Agents per-profile rows (`Settings.tsx:630-678`)
- Replace `Settings.tsx:663`'s `{p.profileId} {p.model ? ...}` stale read **in place** (D-06) with: `[ProfileId, muted Body]` `[EngineDisplayName from live Convex-reactive telemetry, Body]` `[session-override/pinned-default secondary line, Label]` `[pending suffix if in-flight]` `[Swap button — opens the same picker Popover, scoped to "This profile", scope selector hidden/locked since context is already profile-specific]`.
- The existing row's "Edit" button (profile metadata editor) is untouched and stays separate from the new swap affordance — swapping the brain is not profile editing.
- Stub tag (dashed `STUB` chip) appended next to the engine name when the stub adapter is active, matching §1/§2.

### 10. Stub-data indicator (D-16, resolved gray area)
- Two visibility layers, both persistent (never hover-only, per "can never be mistaken for a live reading"):
  1. **Micro-tag** — dashed-border `STUB` chip (Label typography, `--muted-foreground`, not a status color — stub-ness is a data-provenance fact, not a warning) next to every engine-name rendering (pill, badge, picker rows, Settings row) whenever the stub adapter is selected.
  2. **Macro-banner** — one non-dismissible `--status-warn`-toned strip at the top of the picker popover (see §3) — the only surface with enough room for the full sentence-length disclosure, and the one place a user is actively about to trust the data to make a swap decision.
- Both layers key off the same single source of truth: the `VITE_` env flag read once by the adapter module (D-16's "one adapter + env flag" — naming left to planning), never a per-row heuristic.

### 11. Expensive/unknown-model warn+confirm ritual (design spec §6, resolved gray area)
- See §3 (picker row inline expansion) and §4 (global-swap modal addendum). No separate component — this is a *state* of the existing row/modal, not a new surface.

### 12. CLI→API text-mode fallback notice (D-04, resolved gray area)
- `sonner` toast, `--status-warn` tone (not `--status-error` — this is a graceful degrade, not a failure), `ArrowRightLeft` icon, copy per the Copywriting Contract. Fired from wherever the run-event stream surfaces the fallback flag (backend contract detail, not this phase's UI decision).
- Out of this phase's explicit scope (per the 12-item surface list handed down): also badging the individual chat response bubble with a "(fallback)" tag, as design-spec §7 item 5 suggests. Noting it here only so planning isn't surprised if a future phase/contract expects it — this UI-SPEC does not require `ChatBubble` changes.
