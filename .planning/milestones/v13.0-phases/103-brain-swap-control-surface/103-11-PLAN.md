<objective>
Close gap Group D (CR-02, BSC-02): `src/components/brains/BrainPicker.tsx:414-419` never passes
`onSelect` to `CommandItem`, so the component's own designed primary interaction — autoFocus search
input → type → arrow → Enter — is completely non-functional.

Purpose: verified against the installed `cmdk` source, Enter dispatches a `cmdk-item-select` DOM
event to the arrow-highlighted item, whose listener calls `onSelect?.(value)` — a no-op when the
prop is undefined. cmdk's arrow navigation never moves real DOM focus off the search input; it only
flips a `data-selected` attribute. So the only way to actually swap a brain today is a literal mouse
click on the row's nested `<button>`. `src/components/CommandPalette.tsx` is the in-repo precedent
that wires `onSelect` correctly on every one of its items; this file is the sole deviation.
`e2e/brain-swap.spec.ts` drives selection with `.click()`, which is exactly why it never caught this.

CR-02's own note is a hard constraint: a naive `onSelect={() => handleSelect(entry)}` is a
REGRESSION, not a fix — it would skip the inline expand-to-confirm step `103-UI-SPEC.md` §3
specifies for expensive and unknown-tier models, and it would need to keep the D-15 global confirm
gate intact. (Citation note: 103-REVIEW.md's CR-02 text calls that per-row step "D-11". That is a
mislabel — UI-SPEC §§3/11 classify it as a *resolved gray area*, while D-11 governs pinned-default
disclosure in the GLOBAL confirm modal, a different feature. This plan cites UI-SPEC §3.)

This plan also folds in the two warnings that live in the same two files: WR-03 (the focusable
`<span tabIndex={0}>` nested inside the row's `<button>` — the natural companion to a keyboard fix)
and WR-01 (no staleness guard on the scope-driven catalogue fetch).

Output: a keyboard-operable picker whose keyboard path and mouse path share one branch decision.
</objective>
