Add to `hooks/studioWatch.mjs` an exported `encodeThumbnail(candidate, outPath, deps)` that produces
a webp thumbnail of **at most 200 KB**, or refuses.

Constants at module scope with comments: `THUMB_MAX_BYTES` = 200 * 1024, `THUMB_MAX_ATTEMPTS` = 5,
and explicit quality/scale ladders (start around quality 80 with the longest edge capped near
1024 px, stepping both down across attempts to a hard floor).

Algorithm:
1. Choose the invocation by `mediaType`. Stills use a scale + `-c:v libwebp -quality N` encode.
   Video adds the `thumbnail` filter and `-frames:v 1` to take a poster frame before scaling and
   encoding. Audio produces NO thumbnail at all — return a result indicating "no thumbnail", because
   the UI-SPEC renders an `AudioLines` placeholder for audio and a fabricated waveform image would
   be inventing a signal that does not exist.
2. **Use `-quality`, never `-q:v`.** Add an inline comment naming the trap so nobody "fixes" it back.
3. After each encode, `stat` the output and compare against `THUMB_MAX_BYTES`. If over, step down
   the ladder and re-encode. Cap at `THUMB_MAX_ATTEMPTS`.
4. **If the floor is reached and the output is still over cap, REFUSE**: delete the oversized
   temporary output, return `{ ok: false, reason: "THUMB_OVER_CAP", bytes }`, and log a warning
   naming the file. Do not upload it, and do not skip the file silently — the candidate still
   proceeds to ingest in Task 2 with no thumbnail, so the row appears in the gallery with the
   `ImageOff` placeholder rather than vanishing. Getting this wrong in either direction is a real
   bug: uploading violates D-02, dropping the file violates D-07's spirit.
5. Return `{ ok, outPath, bytes, width, height, attempts, quality }` so the caller can send
   `thumbBytes`, `width` and `height` and so tests can assert the search actually stepped.

Invoke ffmpeg through an injected `deps.runFfmpeg(args)` defaulting to a real child-process call.
Pass arguments as an ARRAY — never build a shell string, because filenames in the vault are
operator- and generator-controlled and a shell string is a command-injection surface. Bound each
invocation with a timeout and surface a non-zero ffmpeg exit as a failure, not as a silent success.

**Tests, in `hooks/__tests__/studioWatch.test.mjs`** (mock `runFfmpeg` and `stat`; do not spawn real
ffmpeg in unit tests):
- Under-cap on the first attempt → exactly one invocation, `attempts === 1`. Control: an
  always-oversized mock → exactly `THUMB_MAX_ATTEMPTS` invocations and `ok === false` with reason
  `THUMB_OVER_CAP`. A one-sided test passes against a loop that never iterates.
- A mock that is oversized for two attempts then under → `ok === true`, `attempts === 3`, and the
  quality used on attempt 3 is strictly lower than on attempt 1. Assert the STEPPING, not just the
  final success.
- The refusal path deletes the oversized temp file — assert the unlink call happened.
- Every generated argument list contains `-quality` and does NOT contain `-q:v`.
- Video candidates produce an arg list containing the `thumbnail` filter and `-frames:v`; stills do
  not. Both asserted in the same test.
- Audio candidates produce no ffmpeg invocation at all and a "no thumbnail" result.
- Arguments are passed as an array: assert `runFfmpeg` receives an Array, and assert a filename
  containing a space and a `&` survives intact in the argument value rather than being escaped or
  split.

Add an exported `reconcileTrash(rowsByHash, vaultRoot, deps)` and call it from `main()` after the
ingest pass.

The watcher needs the current `{ contentHash → { deletedAt } }` map. Obtain it through a
bearer-authenticated read against the ingest surface (a GET on `studioHttp.ts` if one exists, or add
one following the same auth-first, no-CORS pattern). Bound the read; do not fetch every row's full
provenance when only two fields are needed.

Three rules, applied per cycle:

1. **Move out.** A file under `gen\` (or `refs\`/`styles\`) whose `contentHash` maps to a row with
   `deletedAt` SET is moved to `trash\`, preserving its filename and moving its sidecar alongside it.
   The row is already hidden from the grid — the mutation did that with no host round-trip — so this
   step is reconciliation, not the delete itself.
2. **Move back.** A file under `trash\` whose `contentHash` maps to a row with `deletedAt` CLEARED
   is moved back to the directory its `kind` implies, sidecar alongside. This is what makes Restore
   whole.
3. **Reclaim orphans.** A file under `trash\` whose `contentHash` matches NO row is deleted from
   disk, sidecar included. This is the self-reconciling half of D-08's 30-day janitor: the janitor
   removes the row after the grace period, and the next cycle removes the file. **No second 30-day
   constant lives here** — two independently maintained deadlines can drift, this rule cannot.

Safety rules, all of which must hold:
- Every source and destination path is resolved and asserted to be inside the vault root before any
  move or unlink. A path that resolves outside the root is refused and logged, never acted on.
- A destination collision never overwrites: append a numeric suffix or refuse, and log which.
- A move failure for one file logs and continues to the next; one locked file must not stop the
  whole reconciliation.
- **A rescan with an EMPTY row map deletes nothing.** An empty map means the read failed or returned
  nothing, and treating "I know of no rows" as "every file is an orphan" would delete the entire
  trash directory on a transient network error. Guard on the read having SUCCEEDED, not on the map
  being non-empty, and refuse to reconcile at all when the read failed.

**Tests** (temp-dir fixtures, injected fs; never the real vault):
- Move-out: a `gen\` file whose row has `deletedAt` set lands in `trash\`, and its sidecar moves
  with it. Control, same test: a sibling `gen\` file whose row has no `deletedAt` stays put.
- Move-back: a `trash\` file whose row has `deletedAt` cleared returns to `gen\`. Control: a
  `trash\` file whose row still has `deletedAt` stays in `trash\`.
- Orphan reclaim: a `trash\` file whose hash is in no row is deleted. Control, same test: a `trash\`
  file whose hash IS in a row (still flagged deleted) survives.
- **Read-failure safety:** with the row read reported as FAILED, assert that zero unlinks and zero
  renames occurred. Then, as the control, with the read reported as SUCCEEDED and returning an empty
  map over a trash directory containing one file, assert exactly one unlink occurred. This pair is
  what distinguishes "the read failed" from "there genuinely are no rows".
- Traversal refusal: a crafted path resolving outside the vault root is refused with no fs call.
- Collision: an existing destination filename does not get overwritten.
