<objective>
Give the per-profile axis the same honest, server-confirmed outcome machine the global axis already
ships — extracted into a hook, because the per-profile path has four render surfaces and no modal.

Purpose: ENGINE-04's whole claim is "server-confirmed rather than optimistic, matching the global
axis's BSC-04 contract". The global axis resolves `confirming -> confirmed` on
`modelOverride === confirmTarget` — the OVERRIDE SLOT from `swap.state`, not a resolved
`model_routing` telemetry row. That distinction is load-bearing: a scoped SET writes the override
and emits only `control_verb_swap`; the telemetry row arrives on the profile's next real
resolution, which for an idle profile may never come. So the confirmation reads the override; the
current-engine display reads telemetry. Both are honest; they answer different questions.
Output: `useProfileSwap`, consumed by the picker, with the five-state suffix rendered on all four
surfaces.
</objective>

**The vocabulary to reuse verbatim** (`GlobalSwapModal.tsx:142-157`, verified live):

```
type GlobalOutcome =
  | { status: "pending" }
  | { status: "confirming" }
  | { status: "confirmed" }
  | { status: "accepted" }
  | { status: "error"; reason: string };

export const GLOBAL_SWAP_CONFIRM_TIMEOUT_MS = 4000;
```

Rename per-instance (`ProfileSwapOutcome`, `PROFILE_SWAP_CONFIRM_TIMEOUT_MS`); do NOT invent a
different set of statuses.

**The bounded dispatch wrapper to reuse** (`GlobalSwapModal.tsx:354-380`): a
`Promise.race([dispatch(cmd).then(ack => ({status: ack.status, error: ack.error})), timeoutPromise])`
inside a `try/catch/finally` that always `clearTimeout`s, with the timeout branch resolving to
`{status:"error", error:"no response from Ástríðr — the command was never delivered"}` after
`GLOBAL_SWAP_DISPATCH_TIMEOUT_MS` (15s). `dispatch` comes from `useCommandDispatch()`
(`GlobalSwapModal.tsx:343`), NOT `useAstridrWS().sendCommand` directly.

**The readback effect to reuse, with the D-05 substitution** (`GlobalSwapModal.tsx:448-458`): the
global axis compares `modelOverride === confirmTarget`. The per-profile path compares
`profileOverrides[profileId]?.model` against `confirmTarget` — the profile's entry in the map plan
109-01 added to `swap.state` and plan 109-04 exposed via `useProfileBrainOverrides()` — NOT
`activeEngines[profileId]`. Comment that substitution explicitly in the hook.

**The timeout-start helper to reuse** (`GlobalSwapModal.tsx:422-426`): a ref-held `setTimeout` that
flips `confirming -> accepted` only if still `confirming`.

**Restore semantics, confirmed:** a scoped restore's readback is the ABSENCE of the profile's id
from the override map — `profileOverrides[profileId] === undefined` — mirroring
`GlobalSwapModal.tsx:537`'s `setConfirmTarget(prior)` where `prior` can be `null` after a global
restore.

**The dispatch command shape** (mirrors `GlobalSwapModal.tsx:511-516` plus `profile_id`):
`{ type: "swap.set", target: "brain", value: <entry.id>, restore: false, profile_id: <profileId> }`
and for a restore, `restore: true` with no `value` (read `SwapSetCommand` at
`ws_commands.py:242-256` to confirm the restore shape before writing it).

**UI-SPEC section C's rendered vocabulary** (Label typography suffix — there is no modal on this path):

| Outcome | Suffix | Treatment | Toast |
|---|---|---|---|
| `pending` | "· switching to {EngineDisplayName}…" | pulsing dot, `--status-info` | none |
| `confirming` | SAME suffix as pending — deliberately collapsed | pulsing dot, `--status-info` | none |
| `confirmed` | suffix removed; base label updates | confirmed-live pulse resumes | "{ProfileName} switched to {EngineDisplayName}." |
| `accepted` | "· not yet confirmed" | static `AlertTriangle`, `--status-warn` — must read as UNCERTAIN, never as in-progress or success | fires ONCE at the timeout: "No confirmation yet that {ProfileName} switched to {EngineDisplayName} — it may still be in progress." |
| `error` | suffix removed; base label stays on the real prior engine | none | "Couldn't switch to {EngineDisplayName} — {reason}. {ProfileName} is still on {CurrentEngineDisplayName}." |

`pending` and `confirming` collapse to one suffix on purpose: the compact trigger has no room for
the fuller copy, and the distinction (has the ack arrived vs are we awaiting the state push) is not
something the operator can act on — both are honestly "not yet true".

`accepted` gets a toast even though the global axis does not, because the global dialog is still
open and visibly showing its `AlertTriangle`; the per-profile popover has already closed and the
operator may be on another page. A silent suffix change that only reveals itself on hover fails
ENGINE-04 in practice.

**Persistence:** the `accepted` suffix has NO further timeout. It persists until either a late
confirmation arrives — resolving to `confirmed` exactly as if no timeout had occurred, including
the normal success toast — or the operator starts a new swap on the same profile, which resets the
machine to `pending`.

**The existing mirror to extend:** `BrainPicker`'s `onPendingChange` prop already mirrors the
pending suffix out to custom-trigger consumers, "formatted identically to the string the default
trigger's own DOM renders" (its own docstring). That is the channel the badge, the composer pill
and the Settings row already use — extend it rather than adding a second one.

|----------|-------------|
| browser → astridr `swap.set` (scoped) | a client-originated mutation of server routing state |
| astridr `swap.state` push → the confirm decision | the server-pushed payload decides whether the UI claims a swap landed |
