### The contract each call site now satisfies

`MetricCard` accepts `state?: MetricState` defaulting to `"ready"`. `useMetricState(value, updatedAt,
{ staleAfter, unavailable })` derives `loading` / `ready` / `empty` / `stale` from a Convex-shaped
value. `unavailable` is CALLER-SUPPLIED and `error` arrives from inside a `SectionErrorBoundary`
fallback -- neither is ever inferred by the hook.

Practical mapping for a typical Convex call site:
- `const data = useQuery(api.x.y)` -> pass `data` and its `updatedAt` (if any) to `useMetricState`,
  spread the derived state onto the tile
- a metric with NO emitter behind it yet -> pass `unavailable: true` explicitly, and record in the
  ledger WHY you know there is no emitter (which query does not exist, which table has no writer)
- a tile inside a boundary fallback -> pass `state="error"` directly

### The live proving ground (deliberately not folded)

`.planning/todos/pending/unbounded-analytics-scans-timeout.md` records that
`analytics:activityHeatmap`, `analytics:toolFlowSankey` and `analytics:tokenSunburst` return "too many
system operations" at current row counts and surface as boundary fallbacks on `/analytics` today.
That todo is deliberately NOT folded into this phase -- the fix is Convex query work. But it IS a live
input: those three real failures are how `unavailable` and `error` get verified against genuine
conditions rather than against a fixture. Leave the todo `pending`.

Phase 121 is what makes this possible at all: `/analytics` now survives a failing `useQuery` because
every panel sits inside its own `SectionErrorBoundary`. Before that, any one of those three throws
blanked the whole route, and a tile could not have rendered an honest `unavailable` because the React
tree was already unmounted.
