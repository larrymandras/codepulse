<planner_corrections>
**1. Reuse the instrument; do not write a second one.** `e2e/polish-geometry.spec.ts:360-459` is this
repo's template for "measure real rendered geometry, log one JSON line, assert on the measured
relationship." Its `sr-only` exclusion and its `rightOverflow`-vs-`scrollOverflow` distinction were
both learned live during Phase 120 and are documented in that file at `:399-411`. Adapt the walker,
scoped to the rules list, into a NEW spec file (`e2e/alert-rules-geometry.spec.ts`) rather than adding
a block to `polish-geometry.spec.ts` — that file is plan 126-04's and a separate concern.

**2. Wait on rendered rows before measuring.** This is the same class of defect plan 126-04 just
fixed. `/alerts` renders its rules from `useQuery`-backed data; a measurement taken on a cold page
records a list that is not there. Wait on a real rendered row (fail-don't-skip, per
`e2e/serif-trial.spec.ts:57-70`), and assert the row count is greater than zero BEFORE recording any
geometry — a zero-row page produces a pitch of `NaN` or an empty culprit list that looks like a pass.

**3. The Radix ScrollArea precedent is a lead, not a finding.** The todo raises Phase 123's
`radix-scrollarea-table-clips-content` defect, where a viewport wraps children in a `display: table`
div that sizes to content width and silently defeats `truncate`/`min-w-0`/`flex-wrap` at the call
site. `AlertRulesEngine.tsx:388` is a plain `div` with `overflow-y-auto`, so that precedent applies
only if a Radix primitive wraps this panel further up the tree. Establishing that is part of the
measurement: walk the ancestor chain and record each ancestor's tag, `display`, and any
`data-radix-*` attribute.

**4. Measure the badge anomaly too, and treat it as possibly unrelated.** One badge rendered `std-hi`
where its siblings render `STANDARD`. `std-hi` is not a visual truncation of `STANDARD` — it looks
like a different VALUE. Record the actual `rule.severity` strings present in the data alongside the
rendered text, so the SUMMARY can say whether this is a layout symptom or a data one. Do not assume
the two symptoms share a cause; the todo's own guidance for the sibling `/automation` item applies
here as well.
</planner_corrections>
