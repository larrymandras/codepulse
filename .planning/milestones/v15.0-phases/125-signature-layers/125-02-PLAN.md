<planner_corrections>
**Why the window is a constant and not an argument.** Three verified facts, each of which alone
would be sufficient:

1. **`windowSeconds` would be attacker-controlled, not app-controlled.** Per `CLAUDE.md`'s
   SEED-008 record, every public Convex function on this deployment is callable with no credential
   by anything that can route to the host — measured 2026-08-11 with a control (a bogus function
   name returns `Could not find public function`, so the probe discriminated). A clamp would help,
   but a constant removes the surface entirely, and D-17 plus the sketch fix the window at 60s
   anyway, so no legitimate caller needs the argument.
2. **An unbounded scan of THIS table is a repeat incident.** `convex/events.ts:200-203` carries it
   verbatim on the analog query: "an unbounded desc scan streams from the very top of the index and
   dies under memory pressure or index garbage (2026-07-22 incident; same fix as heroStats
   2026-07-20)." `convex/retention.ts:40` records the causing state as "~896k runtime_events" and
   `:43` keeps 14 days of them, so a large window reaches roughly that many rows.
3. **A time bound alone is weaker than the analog it copies.** `listRecentUnified` pairs its 48h
   range bound with a hard `.take(fetchCount)` at `convex/events.ts:213`. Both bounds, not either.
   The house read budget is **4,096 READS**, not the 16,000 figure the Convex docs suggest
   (memory `convex-mutation-read-limit-4096`); `.collect()` over a firehose table has no defence
   against that ceiling and `.take(500)` does.

**`truncated` is returned, not swallowed.** If the cap ever binds, the consumer must be able to say
the trace is incomplete rather than drawing a quietly partial one.
</planner_corrections>
