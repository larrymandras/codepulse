<planner_corrections>
Two calls this plan makes that the UI-SPEC left open or would get wrong if read literally.

**1. The freshness timeout is CONNECT-SCOPED, not a rolling staleness timer.**
`125-UI-SPEC.md:166` describes it as firing when no `estop_state` has arrived "for a bounded
interval while the socket remains connected". Read as a rolling timer that is fatal: D-02's push
contract is connect + transition ONLY — there is no heartbeat — so a calm system emits nothing
after its connect snapshot, and a rolling timer would drive every healthy console permanently to
Unknown, making the aurora resting state unreachable and falsifying success criterion 1 outright.
Implement it as: a timer ARMED on mount and on each transition into `wsStatus === "connected"`,
DISARMED by the first well-formed snapshot on that connection, firing once into Unknown if it
expires. `SNAPSHOT_TIMEOUT_MS = 15000` — discretionary and tunable, chosen above
`AstridrWSContext.tsx`'s existing `ACK_TIMEOUT_MS = 10000` so a slow-but-working handshake cannot
flap the horizon. State this in a code comment, not just here.

**2. The warn state's source is a PROP, not a query inside the horizon.**
D-05 puts the horizon on WS only. `SignalHorizon.tsx` therefore takes `alertLevel` as a prop and
contains zero `useQuery` calls; plan 125-08 hoists the ALREADY-EXISTING
`useQuery(api.alerts.countBySeverity)` out of `SystemChip` in `DashboardLayout.tsx` and feeds
both consumers from that one call, so no new Convex subscription is added anywhere.
`alertLevel: "unknown"` (counts still loading) does NOT block resting — the E-Stop snapshot is the
safety gate; alert counts are a severity overlay, and `SystemChip` already renders nothing rather
than a claim while they load.
</planner_corrections>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-125-04-01 | Spoofing | a forged or replayed `estop_state` claiming `armed: false` | mitigate | The socket is auth-gated at upgrade (`ws_telemetry.py` dual-key constant-time check), so an unauthenticated peer cannot push a frame. A stale "all clear" therefore cannot outlive its connection. |
| T-125-04-02 | Spoofing | a DROPPED `estop_state` (the arm event never arrives) | mitigate | This is the dangerous direction and the reason the machine is fail-closed. | T-125-04-03 | Tampering | a MALFORMED `estop_state` payload | mitigate | Validity is gated on `typeof data.armed === "boolean"` — a truthy `"false"` string cannot arm or disarm. Every invalid shape sets `snapshot = null` (Unknown), never "no change". Proven by test (d) across four distinct malformed shapes. |
| T-125-04-04 | Denial of Service | a throw inside the `subscribeEvent` callback | mitigate | `AstridrWSContext.tsx:322-326` fans out inside `ws.onmessage` with no per-subscriber try/catch, so a throw here would kill the whole telemetry stream for every consumer.
