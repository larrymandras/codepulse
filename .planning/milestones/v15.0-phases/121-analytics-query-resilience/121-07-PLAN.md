    condition AND an explicit iteration guard — never an open-ended loop:
      - Stop condition: the returned JSON's `done` field is `true`.
      - Iteration guard: hard cap at 200 iterations. 30 days is 720 hours; at `maxHours: 6` that is

        reason to raise the guard.
      - Between iterations, do not raise `maxHours` above 6. The relevant ceiling on this instance is
        4,096 READS per mutation, not the documented 16,000 writes: `ctx.db.delete()` counts as a read
        and a query issued after N inserts in the SAME mutation costs roughly N extra reads, so the
        insert-then-query tax inside one invocation grows faster than linearly with `maxHours`.
      - Accumulate and record: total invocations, summed `rowsInserted`, and the FULL union of

        recorded as a total is exactly the silent undercount this phase exists to refuse.
      - Watch `docker stats convex-backend` between batches if the run takes long. A dashboard-wide
        "no data / all zeros" symptom during this run is memory starvation until proven otherwise, per
