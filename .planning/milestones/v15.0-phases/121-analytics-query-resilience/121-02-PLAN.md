        8000 matches the existing per-page precedent on this route (`PROVIDER_BREAKDOWN_ROW_CAP`).

        the distinct `provider::model::billingType::goalId` keys active per hour, which at the

        load-bearing, not stylistic: a `gte`-bounded index read returns OLDEST-first by default, so a
        naive `.take(N)` would keep the oldest N buckets and silently drop the newest. Descending keeps
        the newest and drops the oldest end, which is the only acceptable direction for a freshness-
        labelled surface.
      - `const truncated = rows.length >= ROLLUP_READ_CAP;` and, when truncated, a `console.warn`
        naming the query, the cap and the window, in the same loud style as the existing
        `computeHourly` and `subscriptionUsage` truncation warnings. A silent undercount on this
        surface is what the whole phase exists to refuse.

    needs them should read `aggregates` directly rather than through a panel-shaped endpoint.

      `{ rows: Array<{ model: string; calls: number; tokens: number }>, asOf: number | null,

    Drop the `cost` field entirely — same Phase 104 D-01 reason; the money column already comes from

    queries so the panel handles one shape.

    Freshness metadata (D-10), all derived from rows already read — add no extra query:

        OLDER of the two `asOf` values so the label can never overstate freshness; if either read
        returned no rows, `asOf` is `null`.

        same pass that sums the values.
      - `expectedBuckets` = `Math.floor((ROLLUP_LOOKBACK_DAYS * 86400) / 3600)` — pure arithmetic over
        the request window, no read.
      - A docstring on each handler stating the honest limit verbatim in substance: **a zero-activity
        hour is indistinguishable from a missed cron run**, so `presentBuckets` means "hours with
        data" and nothing stronger. Cross-metric disambiguation was considered and deferred (D-10).
        Also state that hourly rollups mean the most recent up-to-60 minutes is permanently absent.
