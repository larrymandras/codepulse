Bifröst, Galdr & Studio

What these three CodePulse surfaces actually do — and why they look like almost nothing when you open them.

Short answer: your read is correct, but the cause isn't what it looks like.

All three are curated libraries — they hold what you deliberately put in them, and none of them seeds itself. Right now they hold 7 rows between them, and 3 of those are leftover test fixtures from the phase that built Studio. The pages are empty because the libraries are empty, not because the features are stubs.

The second cause: for all three, most of the engineering is off-page — HTTP routes agents call, a scheduled file watcher, a version trail, a trash janitor. None of that is visible from the browser, so the pages read as "a grid and four buttons."

Galdr — the prompt library

Galdr stores prompts you want to reuse, and makes the same library reachable from the browser and from any Claude Code session on any machine, with no export step.

The actual mechanism

A prompt is a body of text with {{variables}} in it. The backend detects those variables (one implementation, convex/galdrVariables.ts, shared by the UI and the CLI so they can't disagree) and refuses to deliver a body until every variable has a real value. Blank is not an answer; a partial body never ships.

WhereWhat you can do
The pageNew Prompt · edit (drawer) · favorite · search · filter chips (All / Favorites / Recent / per-category) · Copy, Send to Chat, Copy as command (all three gated behind the fill-in-variables dialog) · version history with restore · archive
From a session/galdr browses categories and favorites · /galdr <slug> key=value fetches, fills and injects a prompt · /galdr-save <title> captures the current conversation back into the library
Over HTTP4 bearer-authed routes: GET /galdr/prompt, GET /galdr/list, POST /galdr/prompt, POST /galdr/usage — deliberately CORS-free, so they're agent-only and a browser can't read them

The invisible parts (this is where the code went)

  • A capped version trail. Every body-changing write snapshots the old body into promptVersions, pruned to the newest 20 per prompt, inline, scoped to a single prompt's index so it can never become a mass delete.
  • Slug uniqueness with no unique index. Convex has none, so a read-then-write inside a transaction stands in for one. A collision refuses with a 409 naming the existing prompt — it never overwrites and never auto-suffixes.
  • Fuzzy lookup that can't auto-inject. A non-exact search returns candidates with no body attached — there is literally nothing to inject until you pick one. A single fuzzy hit still stops and asks.
  • Usage counting that means something. usageCount bumps only on resolved-body delivery, never on browsing, viewing, favoriting, or "Copy as command".

Deliberately not built

by decision No archived-prompt view and no un-archive control. No hard delete anywhere (no mutation exists that could serve one). No category admin — chips are derived from live rows. No seed rows: the page's own source comment says "the library begins genuinely empty and the empty state is the first-run experience."

Bifröst — the link hub

The smallest of the three, and honestly small on purpose: it's a categorised grid of URLs, with a pinned row on top.

The one idea that isn't just a bookmark manager: a link can name a Docker container, and Bifröst joins that against the live container status CodePulse already ingests to show a green/red dot. If a link names no container it shows no dot at all — never a green one, because an absent signal must not read as "up."

OperationBehaviour
Add linkTitle, URL, category, optional container name
Pin / unpinPinned links surface in their own section above the categories
ArchiveSoft delete only — hidden everywhere, never purged. No hard-delete mutation exists.
SearchClient-side across title, URL, category, description
SortPinned first, then explicit order, then newest. An unordered link sorts after every ordered one rather than jumping to the front.

Why it feels thinnest

Because it is. 594 lines total, and three planned pieces were explicitly deferred: drag-to-reorder (the order field ships and is respected — the drag UI doesn't exist), and the /bifrost-scan and /link-add curation skills that would have populated it automatically. With those deferred, the only way links get in is you typing them in the dialog — which is why there are two.

Live rows: CodePulse dev server → http://localhost:5173 (no container, so no dot) and Ástríðr API → http://localhost:8181 (container astridr-agent, so it shows a real dot). Neither is pinned.

Studio — the media gallery

By far the largest of the three, and the one where nearly all the functionality lives outside the page. Studio's actual claim is not "a gallery" — it's provenance: every generated asset arrives with a machine-readable record of the model, provider, prompt and parameters that produced it, and you can copy that recipe back out.

How media gets in — the part you can't see

Nothing in the browser uploads anything. The flow is filesystem-first:

  1. /studio-generate calls a generator backend and writes two files into C:\Users\mandr\media-vault\gen\ — the asset, plus a JSON sidecar holding its provenance. It is the only skill permitted to write sidecars, so the contract can't drift across the eight other media skills.
  2. A scheduled task, StudioWatch, runs a 1,181-line watcher every 5 minutes. It walks the vault, SHA-256 hashes every file (the hash is the row identity, so re-syncing never duplicates), pairs each file with its sidecar, encodes a webp thumbnail under 200 KB with ffmpeg — retrying at lower quality, and refusing rather than shipping an oversized one — uploads the thumbnail, POSTs the row through a bearer-authed /studio/ingest route, and reconciles the trash folder against what Convex thinks exists.
  3. /studio-sync runs that identical code path on demand when you don't want to wait 5 minutes.

So why does it look like not much?

Four distinct reasons, worth separating because they need different fixes:

#CauseFix
1 Empty by design. All three refuse to seed themselves. Galdr's source says so explicitly. Seven rows total, three of them test fixtures. Use them for a week. This is the entire fix for Galdr and Bifröst.
2 The work is off-page. Version trails, content-hash dedup, a 5-minute watcher, bearer-authed agent routes, a trash janitor — ~7,300 lines that render as zero pixels. Nothing to fix; just worth knowing the pages aren't the product.
3 The auto-population never shipped. Bifröst's /bifrost-scan and /link-add skills were deferred, so nothing fills it but manual typing. Build those two skills — Bifröst goes from 2 links to dozens in one pass.
4 Studio's headline interaction is missing. No lightbox, no full-size view. A gallery you can't open images in reads as broken even when it isn't. Reopen that decision — it's the highest-leverage single change across all three.

Where they sit in the app

Galdr, Bifröst and Studio are all in the Command nav group — three of the four "Seiðr Suite" operator surfaces added to milestone v14.0 in August 2026. The fourth, Loom (phase 119, pipeline visualisation), sits in Observe instead, because it answers "what is the system designed to do" rather than "what do I keep here."
